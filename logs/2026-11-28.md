## 二、知识点

### 1. 证书记录数 ≠ 子域数

`crt.sh` 返回的是**证书条目**，一条记录可能对应多个域名：

```
4611 条证书记录
  → 提取 name_value（每条的域名列表）
  → 按 \n 拆开        = 5391 个域名
  → 排除 *. 泛解析    = 5386
  → 去重              = 283 个唯一子域
```

**这一步不做，后面所有扫描都是浪费**——重复域名会让 httpx 跑到重复结果，泛解析会让扫描量翻几十倍。

### 2. fake-ip 会让「DNS 判活」彻底失效

第一次用 `Resolve-DnsName` 判断子域是否存在，结果**所有域名都「解析成功」**，全指向 `198.18.x.x`。

**原因**：本机开着代理（TUN 模式），代理软件用 fake-ip 接管 DNS——**任何域名它都先返回一个假地址**，真解析留给代理去做。

```
198.18.0.0/15 是 fake-ip 的常用段（Clash 默认）
看到这个段出现在解析结果里 → 说明你根本没解析到真实 IP
```

**教训**：判活只能看「应用层有没有响应」，不能看「DNS 有没有记录」。

### 3. 猜子域的命中率有多低

按「攻击价值」猜了 13 个（`test` / `cpanel` / `upload` / `webmail` / `portal` …），**只有 4 个存活，命中率 31%**。

而且**评分最高的 `cpanel` 已经下线**。

第二批换了个来源——**从「当前有效证书」里取**，15 个**全部存活**。

| 来源 | 数量 | 存活率 |
|---|---|---|
| 按经验猜 | 13 | 31% |
| 当前有效证书的 SAN 字段 | 15 | **100%** |
| crt.sh 历史记录全量 | 283 | 需逐个验证 |

**为什么当前有效证书更准**：历史记录里混着已经下线的老域名；当前有效证书说明**这个域名现在还在签证书，多半还在用**。

### 4. 用耗时区分「下线」和「被墙」

```
curl 返回 000 + 耗时 < 0.3s   → 域名已下线（DNS 快速失败）
curl 返回 000 + 耗时 > 3s     → 超时（可能被防火墙 DROP）
curl 返回 2xx/3xx/4xx        → 域名存在
```

**「快失败」和「慢失败」是两种完全不同的失败**：0.18s 就返回说明压根没有这个域名；3 秒以上说明有东西在丢包，域名可能还在。

### 5. 从跳转形态读架构

存活站点按响应分四组：

| 组 | 数量 | 特征 | 说明 |
|---|---|---|---|
| A 主应用 | 3 | `302 → Login`（**相对路径**） | 同一个应用，多个入口 |
| B 白标子站 | 8 | `307 → https://<自己>/rkinsite/login` | 白标部署，共用同一套代码 |
| C 域名规范化 | 2 | `301/302 → www` | 只是跳转 |
| D 默认页/主站 | 2 | `200` + 标题 | 真业务 |

**读法**：

```
302 + 相对路径  → 站点自己知道跳哪，是同一个应用
307 + 绝对 URL  → 被重定向到「另一个域名」，白标
301 → www      → 纯规范化，没有独立内容
```

**这一步的价值**：不扫目录、不发 payload，光看跳转就知道「这 8 个是同一套代码的 8 个牌子」，后面只需要打一套。

### 6. `/rkinsite/` 是共用入口

B 组的 8 个子域全部跳到 `/rkinsite/login`——**白标部署的公共路径**。

**这意味着**：8 个域名共用一个应用，漏洞只修一次就全修；反过来，找到一个漏洞就等于 8 个站点都有。

### 7. 蜜罐的四种判据

整理出四组，两组是「教科书级」：

| 组 | 判据 |
|---|---|
| ① | **一个 IP 上 10 种不相关产品**（ServiceNow + FortiSwitch + CrushFTP + IBM HTTP Server…） |
| ② | 全部返回 **418** + `TencentEdgeOne`（CDN 节点，真实业务不会 418） |
| ③ | **10 个以上端口返回完全相同的字节数**（服务端是同一个模板应答器） |
| ④ | 端口异常多 + 模板渲染报错（`[object Object]` 直接出现在页面上） |

**共同点**：真业务不会「什么产品都有」，也不会「每个端口回一样的东西」。

### 8. 未授权 API 的深挖顺序

这批目标里唯一的高危是一个未授权 API，泄露面从小到大：

```
/api/health     → 泄露 AI 模型名 + Page ID
/api/stats      → 统计
/api/pages      → 56 KB，2 个真实页面的完整配置
/api/settings   → 7 个敏感字段（API Key 脱敏，但 Chat ID 是真值）
/api/prompts    → 13 KB，全部 AI 提示词
```

**顺序是有讲究的**：从 `health`（确认活着）→ `stats`（量级）→ `pages`（业务数据）→ `settings`（凭据）→ `prompts`（内部逻辑）。**一步步确认边界，而不是一上来就 dump**。

## 三、案例 / 命令

### 1. crt.sh 查询与转换

```powershell
# 查询
curl "https://crt.sh/?q=%25.conductexam.com&output=json" -o crt.json

# JSON → 子域清单（拆 name_value、去泛解析、去重）
python -c "import json;d=json.load(open('crt.json'));s=set();[s.update(n.split(chr(10))) for e in d for n in [e['name_value']]];open('subdomains.txt','w').write(chr(10).join(sorted(x for x in s if not x.startswith('*.'))))"
```

### 2. 存活验证（不看 DNS，看响应）

```powershell
httpx -l subdomains.txt -sc -title -td -timeout 5 -o alive.txt
```

耗时判据：

```
000 + <0.3s  → 下线
000 + >3s    → 超时/被丢包
2xx/3xx/4xx  → 存在
```

### 3. 跳转形态分类

```powershell
httpx -l alive.txt -location -mc 200,301,302,307 -o redirects.txt
```

### 4. 蜜罐快速筛查

```powershell
# ① 同 IP 多产品
httpx -u TARGET -td

# ② 状态码 418 / CDN 头
curl -sI "https://TARGET/" | Select-String -Pattern "HTTP/|Server|X-Cache"

# ③ 多端口同长度
nmap -p 1-10000 --open -oG ports.txt TARGET
```

## 四、踩坑

| 坑 | 现象 | 原因 / 解决 |
|---|---|---|
| 用 DNS 判活 | 283 个域名「全部存在」 | fake-ip（`198.18.x.x`）接管了 DNS；只看应用层响应 |
| 按经验猜子域 | 13 个只中 4 个 | 换成「当前有效证书」的 SAN，命中率 100% |
| 把 80 端口的 200 当业务 | 抓到 Apache 默认欢迎页 | `Last-Modified: 2018-12-08`，是没配过的默认页；业务在 443 |
| 把所有存活当独立目标 | 扫了 8 遍同一套代码 | 307 跳同一个 `/rkinsite/`，是白标共用入口 |
| 忽略 418 | 以为是正常错误页 | 418 + CDN 头 = 蜜罐 |
| 见洞就 dump | 容易被封/被溯源 | 从 `health` 到 `prompts` 一步步确认边界 |
| 证书记录直接当子域用 | 数量虚高、重复多 | 要拆 `name_value`、去泛解析、去重 |
