## 二、知识点

### 1. 一个网站是四层，用饭店记

| 层 | 对应 | 在饭店里 | 客人看得见吗 |
|---|---|---|---|
| 13 | HTML / CSS / JS | 门面、菜单、服务员 | 全看得见 |
| 14 | PHP | 后厨 | 看不见 |
| 15 | SQL | 仓库和账本 | 看不见，在后厨里面 |
| 16 | 三个合起来 | 整家店开门营业 | — |

**「服务员」这层的特殊之处**：他在客人眼前干活，跑哪条路、喊哪句话，客人全看得见。所以**前端代码永远是公开的，F12 一按全露**——那些「不许按 F12」的题，本质只是不让你方便地看。

**关键区别是后厨的门关着**：页面上那个「余额不足」的红字只是装饰，真判断在 PHP 里。

### 2. 一次注册的七步

```
① 表单里打字，点提交              ← HTML
② 浏览器把值打包成请求发出去
③ PHP 接住，从 $_POST 里捞值
④ PHP 连库，把值塞进一条 SQL
⑤ 数据库存好，回「成功」
⑥ PHP 生成一段新 HTML 递回去
⑦ 浏览器渲染，用户看到「注册成功」
```

七步走完，一个动态网站就成立。**看得懂这七步，才知道每一环能怎么被玩坏**——③ 决定参数能不能注入，④ 决定拼串，⑥ 决定回显。

### 3. 逻辑漏洞：代码一行 bug 都没有

这一类最反直觉——**每一步都按设计正常工作，但整个流程能被玩坏**。

一句话：**系统是照「正常人会怎么操作」设计的，那我不当正常人。**

| 类型 | 怎么做 | 为什么拦不住 |
|---|---|---|
| **短信轰炸** | 合法地一遍遍请求验证码接口 | 每次请求单独看都合法 |
| **支付逻辑** | 价格在前台算好再提交 → 改成 1 分；数量填负数 | 钱在前台算，等于让客人自己写账单 |
| **越权** | `id=5` 改 `id=6` 看别人订单（水平）；普通用户直连管理员地址（垂直） | 没校验「这条数据是不是你的」 |

**共同点**：请求本身完全合法、靠的是「顺序」和「次数」、只能靠理解业务发现（工具扫不出来）。

**回头看我打过的两道题，其实都在这类里**：

```
投票题：服务端只认会话 id 判「投过没有」，访客标识完全没看
        → 固定会话、每轮换访客标识 → 无限投（状态判断不严谨）

打怪题：伤害值是页面算好再提交的
        → 直接提交 9999 秒 Boss（客户端可控数值）
```

当时只觉得「这题能这么过」，现在能给它们归到标准分类上。

### 4. SQL 注入的本质：分不清「指令」和「数据」

```php
$sql = "SELECT * FROM users WHERE id = $id";
```

程序员的意图是「id 这个位置放一个数字」，但我传的不是数字，是一句话：

```
1 or 1=1     →  WHERE id = 1 or 1=1   →  整张表都出来了
```

**我不是在破解数据库，我是在用数据库听得懂的语言跟它说话。**它分不清哪个词是程序员写的、哪个是我写的，因为我确实写在同一个字符串里。

三种类型按「能拿到多少反馈」排，不是按技术难度：

| 类型 | 页面给我什么 | 做法 |
|---|---|---|
| 联合注入 | 把查询结果显在页面上 | `union select` 把数据拼到显示位 |
| 报错注入 | 不显结果，但报错会带内容 | 故意造错，让报错里包含数据 |
| 盲注 | 什么都不给，页面永远一样 | 只能问「是/不是」，靠页面变不变、响应慢不慢猜 |

**信息量的差别决定了打法**：有回显最好办，有报错次之，全瞎只能硬猜。

### 5. 弱类型 `==` 和 0e 哈希绕过

PHP 的 `==` 会做类型转换，两个「看起来像数字」的字符串会被当数字比：

```php
"0e123456" == "0e999999"    // true —— 都解析成 0
"admin" == 0                // true（旧版本）—— 非数字字符串转成 0
```

**经典利用**：登录处对比 MD5 时用 `==`，就找一个 MD5 以 `0e` 开头、后面全是数字的字符串，两边都会被当成 0。

```
QNKCDZO   → 0e830400451993494058024219903391
240610708 → 0e462097431906509019562988736854
```

**三种比较要分清**：

| 写法 | 行为 |
|---|---|
| `==` | 松散比较，会转类型 |
| `===` | 严格比较，类型和值都要一样 |
| `strcmp` / `in_array` | 前者在数组入参时行为异常，后者默认松散 |

### 6. 数组参数绕过

很多过滤函数只处理「字符串」，传数组过去就直接失效：

```php
strcmp($_GET['a'], "admin")   // 传 a[]=1 → strcmp 返回 null → 松散比较下等于 0 → 通过
in_array($x, $whitelist)      // 松散比较 + 数组入参，容易出意外
```

**前提**：参数名后面加 `[]`（PHP 会把它解析成数组）且代码没有 `is_string()` 检查。

### 7. `information_schema`：注入时枚举结构全靠它

```sql
SELECT schema_name FROM information_schema.schemata;                  -- 所有库
SELECT table_name  FROM information_schema.tables
    WHERE table_schema = 'security';                                  -- 某库的表
SELECT column_name FROM information_schema.columns
    WHERE table_schema = 'security' AND table_name = 'users';         -- 某表的列
```

三句话背下来，注入的「查库 → 查表 → 查列 → 取数据」四步就有了骨架。

### 8. `mysql -h127.0.0.1` 的 `::1` 坑

不加 `-h` 直接 `mysql -uroot -p`，可能报：

```
ERROR 1130 (HY000): Host '::1' is not allowed to connect to this MySQL server
```

**原因**：Windows 下 `localhost` 被解析成 IPv6 的 `::1`，而 root 只授权了 `127.0.0.1`。加上 `-h127.0.0.1` 强制走 IPv4 就好。

| `mysql -uroot -p` 连不上 | `ERROR 1130 Host '::1'` | `localhost` 解析成 IPv6；加 `-h127.0.0.1` |
