## 二、知识点

### 1. stream wrapper 与 libcurl 的协议能力不同（实测清单）

同一台机器、同一个 PHP 进程，两种发请求方式的可用协议**不是一个集合**。

**`stream_get_wrappers()`（`file_get_contents` 走的）**：

```
php  file  glob  data  http  ftp  compress.zlib  https  ftps  phar
```

**`curl_version()['protocols']`（`curl_exec` 走的）**：

```
dict  file  ftp  ftps  gopher  gophers  http  https  imap  imaps
mqtt  pop3  pop3s  rtsp  smb  smbs  smtp  smtps  telnet  tftp
```

**关键差异**：

| 协议 | wrapper | libcurl |
|---|---|---|
| `gopher` | **没有** | **有** |
| `dict` | **没有** | **有** |
| `tftp` / `telnet` / `smtp` | 没有 | 有 |
| `file` / `http` / `ftp` | 有 | 有 |

**结论**：源码里用 `file_get_contents($url)` 还是 `curl_exec($ch)`，直接决定 SSRF 能打多深。前者连 gopher 都没有，后者全套。

这条解释了之前遇到的现象：本机 `file_get_contents('gopher://...')` 直接失败，但 `curl_exec` 能发出去——不是配置问题，是**两种实现的协议集本来就不同**。

### 2. `max_execution_time` 能兜住 curl 阻塞（实测）

一直有个疑问：PHP 的 `max_execution_time` 是不是管不住 curl 这种 C 层的阻塞？

实测：`max_execution_time=2`，curl 自己设 `CURLOPT_TIMEOUT=6`：

```
Fatal error: Maximum execution time of 2 seconds exceeded
```

**在 2 秒时被 PHP 掐掉了，没等 curl 的 6 秒。**

→ **`max_execution_time` 可以作为 curl 阻塞的兜底**。但要注意：它统计的是 CPU 时间还是墙钟时间，在 CLI 和 FPM 下表现可能不同，不能完全替代 `CURLOPT_TIMEOUT`。

### 3. worker 被打满后，扫描会「静默丢端口」

复现思路（`_t_saturate.py`）：

```
① 先并发打 4 个 gopher://...:80/_   （每个会占住一个 fpm worker 约 1 分钟）
② 立刻用和正常扫描一样的 timeout=3 去扫已知开放的端口
③ 看结果是拿到了，还是被 except 吞掉
```

**为什么会静默丢**：worker 满了以后新请求排队，客户端 3 秒超时抛异常，脚本的 `except` 直接把端口当"关闭"处理。

**结果就是：明明开放的端口，扫描器报"没开"。**

**这条是打 SSRF 靶场时最容易误判的坑**——不是漏洞不存在，是自己的探测把靶场打残了。

**对策**：
- 扫描时降低并发（3~5 个足够）
- 先做一次"对照组"（扫一个已知开放的端口）确认靶场还活着
- 挂住的 payload 打完就重启靶场

### 4. gopher 挂住 → 靶场卡死，超时是防御核心

`php -S`、php-fpm 的 worker 都是有数量上限的。一个 `gopher://...:80/_` 这种"发完不关"的 payload，会把一个 worker 长期占住。

连着发几个，靶场就彻底无响应。

**判断标准**：如果所有请求都超时，先怀疑"靶场被自己打挂了"，而不是"漏洞不存在"。

**验证办法**：`docker restart` 靶场后立刻访问首页，能打开说明之前是被打挂了。

### 5. 比赛策略：目标从「深挖」改成「扫完」

看了签到题清单的思路，最大的策略调整是**反着来**：

| 平时练题 | 比赛（签到题为主） |
|---|---|
| 一道题深挖到底 | 每道题先跑一键扫，命中了再深入 |
| 卡住继续想 | 卡 5 分钟就换题 |
| 追求做出难题 | 追求"把送分点全捡完" |

**开场 20 分钟扫场最值钱**：先把所有题点一遍，判断哪些是签到题、哪些要花时间。

### 6. 工具设计上的三个决定

**① 签到题检查要并发**

`tpl_qiandao.py` 用 10 线程，6 道题从 65 秒降到 10 秒内。串行扫场在比赛里是不可接受的。

**② 默认只打印命中的**

没命中就一句话带过，避免刷屏盖住真正的发现。

**③ flag 要统一管理**

`ctf.py` 里做了 flag 记录，避免"拿到了但忘了记"或者重复提交。

### 7. 离线 AI 的定位：查笔记，不是解题

`问AI.py` 的核心设计是**先检索自己的笔记，再让模型回答**：

```
问题 → 检索笔记片段 → 拼进 prompt → "只根据资料回答，没有就说没有"
```

**防幻觉的关键在系统提示**：明确要求"资料里没有就直说"，而不是让它自由发挥。

**它擅长的**：报错翻译、语法速查、把思路变成代码骨架。
**它不擅长的**：想解题思路、生成 payload（会编）。

## 四、踩坑

| 坑 | 现象 | 原因 / 解决 |
|---|---|---|
| 扫描报"端口没开"，实际是开的 | 明明通的端口扫不到 | worker 被打满，请求排队超时被 except 吞掉；降并发 + 重启靶场 |
| 所有请求全超时 | 以为靶场挂了 | 自己发过挂住的 gopher payload，worker 被占满；`docker restart` 立刻恢复 |
| 以为 wrapper 和 curl 协议一样 | `file_get_contents('gopher://')` 失败 | 两种实现协议集不同，wrapper 没有 gopher / dict |
| 以为 `max_execution_time` 管不住 curl | 担心设了也没用 | 实测能掐断，但 CLI 与 FPM 行为可能不同，不能替代 `CURLOPT_TIMEOUT` |
| 串行扫场太慢 | 6 道题 65 秒 | 改并发 10 线程，降到 10 秒内 |
