## 二、知识点

### 1. `account-migration`：一个纯数据校验题

这道题没有漏洞，全是**规则验证**。附件结构：

```
README.txt              规则说明（v4）
manifest.json           对象索引 + 分支表 + cutoff
base.json               初始状态
objects/*.json          每个提交对象
commit-journal.json     提交日志
replica-receipts.json   镜像确认
revocations.json        撤销记录
```

**对象长这样**：

```json
{"before": "6c7c7634...", "operations": [{"field": "owner", "value": "subject_457723576"}],
 "parent": "ROOT"}
```

**判一个 COMMIT 是否有效，要同时满足四件事**：

| 条件 | 含义 |
|---|---|
| 索引的 ID / 分支 / 修订号一致 | manifest 里的记录和对象本身对得上 |
| 对象 SHA 一致 | 文件没被改过 |
| 镜像确认 SHA 一致 | 副本那边也认这个提交 |
| 两侧时间都不晚于 cutoff | 截止之后的提交不算 |

再排除四类：**截止前被撤销的、损坏的、缺确认的、祖先无效的**。

**重放规则**（这题的核心）：

```
① 在该分支选修订号最大的「有效」提交
② 沿 parent 一路回溯到 ROOT
③ 从 base.json 开始重放
④ 每步先验证 before（必须是上一步状态的哈希）
⑤ 再按 operations 依次覆盖 field
⑥ 跨分支的祖先不允许
⑦ 最终 owner 要和目标 handle 一致
```

**这里最关键的细节是「状态序列化规范」**：

> 状态按 UTF-8 JSON 序列化：**键排序、无多余空格、保留 Unicode**

因为 `before` 字段存的是**上一步状态的 SHA256**。序列化差一个空格、键的顺序变了，哈希就对不上，整条链就断了。

**这跟 Git 的 tree object 是同一个思路**——内容寻址要求序列化必须完全确定。

### 2. 这道题的时间陷阱（最容易错的地方）

README 里专门写了两条警告：

```
日志的 time 是迁移入账时间，不是注册时间。
不要按原始字符串排序时区时间。
```

**正确的算法**：

```
registration_commit → 找到同 ID 的提交 → 取 creation_tick_ms（快钟记录的 Unix 毫秒）
→ 减去 clock_correction_ms（时钟校正量）
→ 得到真实 UTC 时间
→ 转北京时间（UTC+08:00）
→ 取日期 YYYY-MM-DD
```

**为什么容易错**：

| 错法 | 后果 |
|---|---|
| 用 journal 里的 `time` | 那是入账时间，不是注册时间 |
| 不减 `clock_correction_ms` | 服务器时钟快，算出来差几分钟，跨天就错一天 |
| 按字符串排序时间 | `2026-08-13T20:40:00+08:00` 和 `2026-08-13T12:40:00Z` 是同一时刻，字符串比较会排错 |
| 忘记转时区 | UTC 和 UTC+8 差 8 小时，晚上 20 点之后就会跨天 |

**这类题的核心不是技术，是老老实实按规范一步步走，任何一步偷懒都错。**

### 3. CVE 复现的工程化：双端口对比

今天把 CVE-2025-68664（LangGrinch）做成了**两个容器、两个端口**：

```
5055  →  漏洞版（1.2.4）
5056  →  已修复版（1.2.5）
```

**为什么值得这么搭**：

| 好处 | 说明 |
|---|---|
| 一个脚本跑两边 | 同一份 exploit，只改端口号，结果一成一败，这就是证据 |
| 不用切 PYTHONPATH | 不装两次包、不改环境变量 |
| 能留下日志 | `5055-vuln-app.log` / `5056-fixed-app.log` 直接当报告材料 |

**这是验证漏洞最标准的做法**：`同一个输入 + 两个版本 = 一个成功一个失败`。

### 4. 把「写死的攻击数据」改成「从外部读」

原来的复刻脚本里，攻击 payload 是写死在代码里的字典：

```python
attacker_dict = {"lc": 1, "type": "secret", "id": ["OPENAI_API_KEY"]}
```

改成从文件/命令行读：

```powershell
python cve复刻-从输入读.py payload.json
```

**这一步很重要**：写死在代码里等于「我知道格式所以能构造」，从外部读才是「**用户提交的数据能触发漏洞**」——这才叫漏洞，否则只是演示。

之前每次打完一发，靶场就挂（worker 被挂住的连接占满）。今天做了三件事：

### 2. 状态哈希的正确算法（伪代码）

```python
# 关键：序列化必须是确定性的
canonical = json.dumps(state, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
assert hashlib.sha256(canonical.encode("utf-8")).hexdigest() == obj["before"]
```

三个参数缺一不可：
- `sort_keys=True` → 键排序
- `separators=(",", ":")` → 去掉多余空格
- `ensure_ascii=False` → 保留 Unicode（不转成 `\uXXXX`）

### 3. 时间换算

```python
utc_dt = datetime.fromtimestamp((creation_tick_ms - clock_correction_ms) / 1000, tz=timezone.utc)
bj = utc_dt.astimezone(timezone(timedelta(hours=8)))
print(bj.strftime("%Y-%m-%d"))
```

## 四、踩坑

| 坑 | 现象 | 原因 / 解决 |
|---|---|---|
| 状态哈希对不上 | `before` 和上一步算出来的不一致 | JSON 序列化不规范：键没排序、有多余空格、Unicode 被转成 `\uXXXX` |
| 时间算出来差一天 | 日期差 1 | 忘了减 `clock_correction_ms`，或没转北京时间 |
| 按字符串比时间 | 排序结果怪 | `+08:00` 和 `Z` 是同一时刻但字符串不同，必须转成 datetime 再比 |
| 用了 journal 的 `time` | 注册日期错 | 那是迁移入账时间，不是注册时间 |
| 攻击 payload 写死在代码里 | 演示得了，说不清是漏洞 | 改成从文件读入，才符合「用户输入触发」 |
| 靶场打完就死 | 要重启整个环境 | 改造成可重启（entrypoint + compose.lab.yml） |
