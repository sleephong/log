## 二、知识点

### 1. `launch-failed` / `exitCode=18` 是「沙箱起不了子进程」，不是「程序崩溃」

这是 **进程创建阶段**的失败，不是运行阶段。区分方法：

| 症状 | 含义 |
|---|---|
| `render-process-gone: reason=launch-failed` | 子进程**根本没被创建出来** |
| `render-process-gone: reason=crashed` | 子进程起来了，然后崩了 |
| `exitCode=18` + `GPU process launch failed: error_code=18` | Windows 上 Chromium 沙箱创建子进程失败的固定签名 |

推论很实用：**这类失败一定发生在"读数据之前"**，所以拿它去怀疑会话/插件/配置都是南辕北辙。

### 2. 判「崩没崩」要看退出码，别等报错窗口

Electron 用 `base::debug::BreakDebugger()` 主动中止时，**Windows 事件日志里查不到 Application Error / WER 记录** —— 因为它不是"崩溃"，是程序自己调的断点。

所以：

```powershell
$p = Start-Process -FilePath $exe -PassThru
Start-Sleep -Seconds 15; $p.Refresh()
if ($p.HasExited) { "code=$($p.ExitCode)  hex=0x$('{0:X8}' -f $p.ExitCode)" }
```

`0x80000003` 一出现，直接往「Chromium FATAL」方向查，不要浪费时间翻事件日志。

### 3. `ELECTRON_RUN_AS_NODE` 会污染从 DSH 里启动的 Electron 程序

这个坑很隐蔽：DSH 的宿主进程给它的 node 子进程设了 `ELECTRON_RUN_AS_NODE=1`，**这个变量会被 shell 继承**。于是从 DSH 的 shell 里启动另一个 Electron 应用时，那个应用会**以 Node 模式运行**：

```
DSH Desktop.exe: bad option: --enable-logging=stderr
```

不带参数时更糟 —— Node 读 stdin 到 EOF，**静默退出、退出码 0、什么都不写**，看起来就像"应用自己消失了"，极容易误判。

**从 DSH 里做 Electron 应用的启动实验，先 `Remove-Item Env:ELECTRON_RUN_AS_NODE`。**

### 4. 新旧两个 dsh 应用共用同一个 Chromium userData

旧应用启动时要创建 `%APPDATA%\@deepseek-ai\dsh-desktop\lockfile`，而**那个目录现在归新版所有**。表现为：

```
ERROR:chrome\browser\process_singleton_win.cc:446] Lock file can not be created! Error code: 5
[desktop] Another instance is already running; focusing existing window and exiting.
```

在**确认没有任何旧应用进程**的情况下也能复现 —— 不是残留进程，是真的在抢同一个目录。

**结论：新版开着的时候，旧版永远打不开**（退出码 0 静默退出，看着就像"点了没反应"）。这和 23:12 那次渲染进程失败是**两个独立的问题**。

### 5. 会话「能不能显示」是三件套，不是单个文件

| 层 | 文件 | 缺了会怎样 |
|---|---|---|
| 正文 | `sessions\--D-deepseek--\<id>\session.vN.jsonl.zstd` | 没有内容 |
| 投影 | `storages\session_projcache\sessions\<id>.json` | 侧边栏只剩裸 ID，没有标题/时间/token 统计 |
| 登记 | `storages\workspace.json` 的 `sessionIds` | **完全不出现在侧边栏** |

这次就踩到第三条：**6 个会话躺在磁盘上，但从来没进过 `sessionIds`**，所以旧侧边栏里也看不到它们。

### 6. 插件的真实存放位置是 `.generations`，不是 `node_modules`

`.generations` 在 **`profiles\` 下，不在 profile 目录里**：

```
%APPDATA%\dsh-desktop\harness\profiles\.generations\live\<genId>\node_modules\<pkg>\
                                              \staging\
                                              \trash\
                                              \desired.json     ← 当前生效的清单
%APPDATA%\dsh-desktop\harness\profiles\web\node_modules\    ← 只是指过去的链接
```

profile 的 `package.json` 用 `pnpm.overrides` 以 `link:../.generations/live/...` 指过去。所以**拷插件不能只拷 node_modules**，要连 `.generations` + `desired.json` + `package.json` 的 overrides 一起。

### 7. 附件是内容寻址存储

```
harness\attachments\v1\objects\<hash前2位>\<完整sha256>
                    \request-images\
                    \tmp\
```

按内容哈希分片存放，**没有扩展名**。所以"附件"和"会话"是两套独立的存储，做备份时容易漏（我就漏了一轮）。

## 三、案例 / payload

### 1. 不用任何 DSH 组件读会话日志（多帧 zstd）

会话日志是**多个 zstd 帧拼接**的，Node 的 `zstdDecompressSync` 一次只吃一帧，直接喂整个文件会失败。要自己按帧头切：

```js
import { readFileSync } from 'node:fs';
import { zstdDecompressSync } from 'node:zlib';

/* 返回从 off 开始的第一帧总长度；-1 表示这里不是帧头 */
function frameEnd(buf, off) {
  if (off + 9 > buf.length) return -1;
  if (buf.readUInt32LE(off) !== 0xfd2fb528) return -1;   // zstd magic
  let p = off + 4;
  const fhd = buf[p++];
  const fcsFlag = fhd >> 6, singleSegment = (fhd >> 5) & 1, dictIdFlag = fhd & 3, checksum = (fhd >> 2) & 1;
  p += [0, 1, 2, 4][dictIdFlag];
  if (!singleSegment) p += 1;
  let fcsSize = [0, 2, 4, 8][fcsFlag];
  if (fcsFlag === 0 && singleSegment) fcsSize = 1;
  p += fcsSize;
  for (;;) {                                              // 逐块走完这一帧
    if (p + 3 > buf.length) return -1;
    const bh = buf.readUIntLE(p, 3); p += 3;
    const last = bh & 1, btype = (bh >> 1) & 3, bsize = bh >> 3;
    p += btype === 1 ? 1 : bsize;
    if (last) break;
  }
  if (checksum) p += 4;
  return p - off;
}

const buf = readFileSync(logPath);
let off = 0; let text = '';
while (off < buf.length) {
  const len = frameEnd(buf, off);
  if (len <= 0) break;
  text += zstdDecompressSync(buf.subarray(off, off + len)).toString('utf8');
  off += len;
}
```

每行是一条 JSON 记录。**坏帧计数 = 0 就说明数据完好**，可以放心做任何迁移。

### 2. 判断「打不开」是不是单实例锁

```powershell
# 先确认真的没有残留进程
Get-Process -Name "DSH Desktop" -ErrorAction SilentlyContinue | Stop-Process -Force
Start-Sleep -Seconds 12
# 再把 stderr 抓出来，看是不是 "Another instance is already running"
$p = Start-Process -FilePath $exe -ArgumentList '--no-sandbox' -RedirectStandardError "$env:TEMP\e.log" -PassThru
Start-Sleep -Seconds 14
Get-Content "$env:TEMP\e.log" | Select-Object -First 5
```

看到 `Lock file can not be created! Error code: 5` + `Another instance is already running`，就是 userData 冲突，不是应用坏了。

### 3. 合并 `workspace.json`（不动默认工作区）

```js
const uniq = (a) => [...new Set(a)];
const merged = structuredClone(newWs);
merged.global.workspaceIds       = uniq([...newWs.global.workspaceIds,       ...oldWs.global.workspaceIds]);
merged.global.pinnedSessionIds   = uniq([...newWs.global.pinnedSessionIds,   ...oldWs.global.pinnedSessionIds]);
merged.global.archivedSessionIds = uniq([...newWs.global.archivedSessionIds, ...oldWs.global.archivedSessionIds]);
for (const [id, w] of Object.entries(oldWs.tables.workspaces)) {
  merged.tables.workspaces[id] ??= w;                 // 保留新版的默认工作区
}
merged.global.defaultWorkspaceId = newWs.global.defaultWorkspaceId;   // 不偷偷改默认
```

改之前**先备份原文件**；这个文件运行中的应用手里有内存副本，可能被写回覆盖，所以迁移脚本要写成**幂等**的，被覆盖了重跑一次即可。
