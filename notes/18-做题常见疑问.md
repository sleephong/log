## 一、Shell 与 curl

### Q1. `curl -s "$T/.git/HEAD"` 里 `$` 是什么、`-s` 是什么？

**分属两层，互不相干：**

| 符号 | 属于 | 作用 |
|---|---|---|
| `$T` | **shell** | 变量展开（纯文本替换） |
| `-s` | **curl** | silent，不显示进度条/错误 |

**`$` 的关键点：curl 从来没见过 `$T`。**

```
你敲的:      curl -s "$T/.git/HEAD"
                  ↓ shell 先替换
curl 收到:   curl -s "http://challenge-xxx:10800/.git/HEAD"
```

**引号规则（实测）：**

| 写法 | 结果 |
|---|---|
| `echo $T` | 展开 |
| `echo "$T"` | **展开**（双引号内也展开） |
| `echo '$T'` | **不展开**（单引号是绝对字面量） |

**`-s` 的坑：它连错误也吞掉。**

| 命令 | 连不上时 |
|---|---|
| `curl URL` | `curl: (7) Failed to connect ...` |
| `curl -s URL` | **（什么都没有）** |
| **`curl -sS URL`** | `curl: (7) ...` ← **推荐** |

**`-s` 和另外三个别混：**

| 参数 | 作用 |
|---|---|
| `-s` | 静默（进度条 + 错误都不显示） |
| `-S` | 显示错误（配 `-s` 用） |
| `-o 文件` | **正文**写到文件（`/dev/null` = 丢掉） |
| `-w 模板` | 输出指定信息（`%{http_code}` = 状态码） |

所以 `curl -s -o /dev/null -w "%{http_code}\n" URL` = **"我只要状态码，别的都别给我"**。

### Q2. 两行命令合成一行，`&&` 和 `;` 有区别吗？

**有，而且很关键。**

| 写法 | 语义 | 前一条失败时 |
|---|---|---|
| `A` 换行 `B` | 顺序执行 | **B 照样跑** |
| `A ; B` | 同上 | B 照样跑 |
| **`A && B`** | **A 成功才跑 B** | **B 不跑** ✅ |
| `A \|\| B` | A 失败才跑 B | — |

**实际踩到的：**

```bash
cd /不存在的目录           # 报 No such file or directory
python2 GitHack.py ...    # ← 照样执行！但在【原来的目录】里
                          #   → python2: can't open file 'GitHack.py'
```

**报错看着像"GitHack.py 不存在"，实际是 `cd` 没成功。**

**→ 写脚本用 `&&`。**

### Q3. 变量什么时候会"消失"？

```bash
T="http://xxx"      # 只在【当前这个 shell 进程】里存在
```

| 情况 | 还有效吗 |
|---|---|
| 同一窗口下一条命令 | ✅ |
| **换终端窗口** | ❌ |
| `sudo bash` / 脚本执行完 | ❌ |

**这是"刚才还能用，现在报错"的头号原因。**

**`${T}` 花括号的作用 —— 界定变量名边界：**

| 写法 | shell 怎么理解 |
|---|---|
| `"$T/.git"` | 变量名 `T`（`.` `/` 不是变量名字符）→ ✅ |
| `"${T}abc"` | 明确 `T` 结束 → ✅ |
| `"$Tabc"` | 找名叫 **`Tabc`** 的变量 → ❌ 空 |

## 二、Python 与工具

### Q4. 为什么 GitHack 必须 `python2`，写 `python` 或 `python3` 都不行？

**因为 Kali 上 `python` 就是 `python3`：**

```
python   → /usr/bin/python    Python 3.14.7
python2  → /usr/bin/python2   Python 2.7.18
python3  → /usr/bin/python3   Python 3.14.7
```

**而 GitHack 是 2017 年的 Python 2 代码，有三类不兼容：**

**① 模块改名（import 直接失败）**

| 文件:行 | Py2 | Py3 |
|---|---|---|
| `lib/common.py:11` | `import urlparse` | `from urllib.parse import urlparse` |
| `lib/request.py:10` | `import urllib2` | `import urllib.request` |

实测：`ModuleNotFoundError: No module named 'urlparse'`

**② 异常语法（最阴险）**

```python
except IOError, ex:      # Py2 语法：捕获并绑定到 ex
```

**Python 3 不报语法错误，而是把它解析成"异常类型的元组"：**

```
handler.type 节点类型: Tuple        ← ast.parse 实测
运行时: NameError: name 'ex' is not defined. Did you mean: 'hex'?
```

**原因**：Py3 的 `except` 语法是 `except [表达式 [as 名字]]`，`IOError, ex` 成了一个**元组表达式** → 被当成"捕获 IOError 或 ex 这两种异常"。

**所以就算把 import 修好，跑到异常处理那行照样炸，而且报错完全指不到问题本质。**

**③ bytes/str 语义**（Py3 严格区分，GitHack 用 `mmap`/`struct`/`zlib` 处理二进制对象）

**结论：不修，直接用 `python2`。** Kali 源里还有 `python2 2.7.18-3`。

### Q5. `cd ~/tools/githack/GitHack-master` 是必需的吗？

**不是。** GitHack 用**脚本自身位置**定位根目录：

```python
paths.GITHACK_ROOT_PATH = os.path.dirname(os.path.realpath(__file__))
```

**`dist/` 也建在工具根目录，不随当前目录变。** 实测在 `/tmp` 下跑，`/tmp/dist` 不存在，`~/tools/githack/GitHack-master/dist` 有。

**那 `cd` 为什么存在？** 为了后面那条相对路径：

```bash
cd ~/tools/githack/GitHack-master     # ← 为了让下面这条能找到
cd dist/challenge-xxx_10800            # 相对路径
```

**更稳的写法（不依赖 cd）：**

```bash
G=~/tools/githack/GitHack-master
python2 "$G/GitHack.py" "$T/.git/"
cd "$G"/dist/*/          # 或用绝对路径
```

### Q6. GitHack 第二次跑会重新下载吗？

**不会。** 实测输出：

```
[-] [Skip][First Try] .../dist/challenge-xxx_10800/.git already exists.
[*] Valid Repository
```

## 三、Git 基础

### Q7. `HEAD` 是什么？每个文件都有吗？

**整个仓库一个，不是文件级的。**

```
.git/HEAD          ← 当前指向（一行，会被覆盖）
.git/logs/HEAD     ← HEAD 的变更历史（只追加，永不删）
```

**`HEAD` 里存的不是哈希，是"分支名"：**

```bash
$ cat .git/HEAD
ref: refs/heads/master

$ cat .git/refs/heads/master
43619cf87c55b884c175dfe32700a1d354d8d774     ← 哈希在这
```

**三层指针链：**

```
HEAD  ──"ref: refs/heads/master"──→  refs/heads/master  ──哈希──→  提交
```

**为什么绕一圈**：`checkout` 切分支只改 HEAD 那行；`commit` 只改分支文件。**两个文件各管一件事。**

**每个文件有没有 HEAD？没有。** 文件的版本记录在：

```bash
git ls-files --stage     # index 里：权限 + blob 哈希 + 文件名
git ls-tree HEAD         # tree 里：同上
```

**有 blob 哈希，没有 HEAD。**

**`HEAD~1` = 往上 1 代：**

```
HEAD    = 43619cf  remove flag
HEAD~1  = 865d08a  add flag
HEAD~2  = ba0f6ab  init
```

### Q8. 短哈希会"自动补全"吗？前五位独一无二就行？

**git 会"解析"，但 bash 不会"补全" —— 两件事。**

**① git 认短哈希（实测）：**

| 输入位数 | 结果 |
|---|---|
| 40 / 12 / 10 / 7 / 5 / **4** | ✅ 能解析（只要在对象库里**唯一**） |
| **3 / 2 / 1** | ❌ `fatal: Needed a single revision` |

- **4 位是硬下限**（git 源码 `MINIMUM_ABBREV = 4`），更短会被当"引用名"解析
- 前缀不唯一 → `error: short object ID xxx is ambiguous`
- **大写也认**（`95956B3` ✅）
- `git log --oneline` 默认输出 **7 位**
- 规范化：`git rev-parse --short <哈希>`

**② Tab 补全不认哈希**

| Tab 能补 | 例子 |
|---|---|
| ✅ 文件名/目录 | `cd ~/tools/git<Tab>` |
| ✅ 命令名 | `pyth<Tab>` → `python2` |
| ✅ 分支/tag | `git checkout ma<Tab>` |
| ❌ **提交哈希** | `git show 9595<Tab>` → 没反应 |

**所以哈希只能从 `git log --oneline` 复制。**

### Q9. `<rev>:<path>` 和 `<rev> -- <path>` 有什么区别？

| 写法 | 输出 |
|---|---|
| `git show 'stash@{0}:30172337317370.txt'` | **文件原文** |
| `git show 'stash@{0}' -- 30172337317370.txt` | 该文件的 **diff** |

**冒号 = 取内容，`--` = 过滤 diff。**

**path 规则：**

| 写法 | 说明 |
|---|---|
| `HEAD:index.html` | 仓库**根目录**下 |
| `HEAD:dir/file.txt` | 子目录用 `/` |
| `HEAD:./file.txt` | ❌ 相对当前目录不生效 |
| `HEAD:/file.txt` | ❌ 前导 `/` 不对 |

**等价关系（md5 实测）：**

```
git show 'rev:path'  =  git cat-file -p <该路径的 blob>
```

### Q10. `@{0}` 和 `stash@{0}` 是一回事吗？

**不是。**

```
stash@{0}    → 636c1f32...   ← stash 本体
refs/stash   → 636c1f32...   ← 同一个
@{0}         → a7aecb50...   ← ★ HEAD 的 reflog 第 0 条（不是 stash！）
```

| 写法 | 含义 |
|---|---|
| `@{N}` | **HEAD** 的 reflog 第 N 条 |
| `stash@{N}` | **refs/stash** 的 reflog 第 N 条 |

## 四、git 命令的隐藏规则

### Q11. 为什么 `git log --all -p | grep` 有时一条都抓不到？

**因为目标是个"合并提交"，`git log -p` 默认跳过它。**

**实测（同一 stash，`grep 'ctfhub{'` 命中数）：**

| 命令 | 命中 |
|---|---|
| **`git log --all -p`** | **0** ❌ |
| `git log --all -p -m` | 2 ✅ |
| `git log --all -p -c` | 1 ✅ |
| `git log --all -p --cc` | 1 ✅ |
| `git show 'stash@{0}'` | 1 ✅ |
| `git stash show -p` | 1 ✅ |

**git 的规则：**

```
普通提交（1 个父）:  diff 相对父提交 → -p 输出
合并提交（2+ 父）:   相对哪个父没唯一答案 → -p 默认【不输出】
                     需要显式 -m / -c / --cc
```

---

### Q12. combined diff 的行前缀为什么是 `++`？

**实测（`cat -A`，`$` 是行尾）：**

```
git log -p -m        → +ctfhub{...}$        ← 1 个 +
git show stash@{0}   → ++ctfhub{...}$       ← ★ 2 个 +
git stash show -p    → +ctfhub{...}$        ← 1 个 +
```

**因为要按"相对每个父"分列标 —— 2 个父就是 2 个 `+`。**

**所以扫 flag 时正则别写太窄：**

| grep 写法 | combined diff 能命中吗 |
|---|---|
| `grep ctfhub` | ✅ |
| `grep '^+'` | ✅（`++` 也以 `+` 开头） |
| **`grep '^+ctfhub'`** | ❌ **漏**（实际是 `++ctfhub`） |
| `grep '^[+-][^+-]'` | ❌ **漏** |

> **我自己就踩过**：早期用 `^[+-][^+-]` 想排除 `---`/`+++` 文件头，结果连 `++` 前缀的改动行一起排除了，误判成"`--cc` 出不来"。

### Q13. `git rm` 之后对象还在吗？

**在。`git rm` 只删"引用"，不删"对象"。**

```
git rm secret.txt && git commit
    ↓
工作区删掉、index 删掉、新 tree 不再指向它
    ↓
但 .git/objects/ 里的 blob 【原封不动】
```

**彻底删除必须两步：**

```bash
git reflog expire --expire=now --all
git gc --prune=now
```

**绝大多数人只做 `git rm`** —— 这就是 99% 的 Git 泄露还能挖到东西的原因。

## 五、题型判断

### Q14. `objects/` 返回 200 和 403，做法差很多吗？

**差很多 —— 200 只要 2 条命令。**

| 状态码 | 路线 | 依赖 | 难度 |
|---|---|---|---|
| **200**（能列目录） | `wget -r` 爬目录树 | 只要 `wget` | ⭐ |
| **403 / 404**（不能列） | GitHack 按哈希取 | GitHack + python2 | ⭐⭐⭐ |

**200 的两条命令：**

```bash
wget -q -r -np -nH --cut-dirs=1 -R "index.html*" "$T/.git/" -P ./dumped
cd dumped && git --git-dir=. log --all -p | grep -i ctfhub
```

**⚠️ 两个坑：**
- `-R "index.html*"` 不能省（目录列表页会污染仓库）
- **`--cut-dirs=1` 会把 `.git` 这一层削掉** → `dumped/` 的内容**就是 `.git` 本身**，不是 `dumped/.git/`

**403 为什么还能取：**

```
哈希 = b738565f...
路径 = .git/objects/b7/38565f48...

路径由【内容】决定 → 知道哈希就能直接取 → 不需要列目录
而哈希就在 reflog 里 → 两条信息合起来就通了
```

### Q15. `.git/index` 返回 200，是不是就是 Index 题？

**不是！`.git/index` 每个 git 仓库都有。**

**判断 Stash 题的正确依据是 `refs/stash`：**

```bash
curl -s -o /dev/null -w "%{http_code}\n" "$T/.git/refs/stash"
# 200 → Stash 题
# 404 → 继续看 logs/HEAD
```

**我自己就差点被误导** —— 探测时看到 `index` 200，第一反应是 Index 题；后来发现 `refs/stash` 也在，而且 index 里只有两个普通 html，才确认是 Stash 题。

---

#### 补充：怎么判断**真的**是 Index 题（2026-10-20 踩坑后补）

**我曾用"index 有几个条目"来判断，结果判错了：**

```
实例 79a64f7a 的探测结果：
  /.git/index  → 200 / 297 字节 / DIRC 版本2 / 3 个条目
                                          └──┬──┘
                              我以为是"比通常多一个" → 误判成 Index 题
```

**实际：HEAD 的 tree 也是 3 个文件，index 和 HEAD 完全一致 → 不是 Index 题。**

**✅ 真正的判据：index 里存在一个 blob，它不在任何 commit 的 tree 里。**

```bash
# index 里的 (文件名 blob)
git ls-files --stage | awk '{print $4"\t"$2}' | sort > /tmp/idx

# HEAD 里的 (文件名 blob)
git ls-tree -r HEAD | awk '{print $4"\t"$3}' | sort > /tmp/head

# 差集：有输出 = Index 题
comm -23 /tmp/idx /tmp/head
```

**实例 79a64f7a 实测差集 = 0 行（无差异）。**

**那它到底是什么题？** 它是"flag 根本没被删"的最简变体：

```
refs/stash 404
git log --all --oneline 只有 2 条：init → add flag     ← 没有 remove flag
ls → 4881604215590.txt 直接在【工作区】里
cat 4881604215590.txt → ctfhub{...}
```

**教训：`ls` 里看到陌生的随机名 `.txt`，先 `cat` 一下再说 —— GitHack 的 `reset --hard` 可能已经把它摆出来了。**

### Q16. Log 题和 Stash 题怎么区分？

| 判据 | Git Log | Git Stash |
|---|---|---|
| `refs/stash` | 无 | **200（41 字节）** |
| `logs/HEAD` 行数 | 3（纯 commit） | **4（多一行 `reset`）** |
| `git log --all` 有 `WIP on` | ❌ | ✅ |
| flag 在哪 | **普通提交的 blob** | **stash 提交的 tree** |
| 关键命令 | `git log --all -p \| grep` | **`git stash show -p`** |

**`logs/HEAD` 的动作序列对比：**

```
Log 题：  commit(initial) → commit → commit
Stash 题：commit(initial) → commit → reset: moving to HEAD → commit
                                       └───────┬───────┘
                                    多出这一行
```

## 六、Stash 专题

### Q17. `stash@{0}: WIP on master: 805a403 add flag` 什么意思？

```
stash@{0}: WIP on master: 805a403 add flag
└──┬──┘└┬┘  └┬─┘ └──┬──┘  └──┬──┘  └──┬──┘
   │   │    │      │        │        └─ 那次提交的说明（subject）
   │   │    │      │        └─ ★ 短哈希（= parent 1）
   │   │    │      └─ 分支名
   │   │    └─ on
   │   └─ reflog 索引，0 = 最新
   └─ 引用名 refs/stash
```

**翻译："这是栈顶那个 stash，是在 master 上、基于 `805a403`（add flag）那次提交做的。"**

**格式是 git 硬编码的：**

```
WIP on {分支名}: {parent1 的短哈希} {parent1 的 subject}
```

**实测验证：**

```
stash 的 parent 1   : 805a403a4104d5dfab660dad9b81fc1ddd52d0ae
parent 1 的短哈希   : 805a403        ← 和 message 里一致 ✅
parent 1 的说明     : add flag       ← 和 message 里一致 ✅
```

**三兄弟的 message：**

| 提交 | message |
|---|---|
| stash 本体 | `WIP on master: 805a403 add flag` |
| parent 2 | `index on master: 805a403 add flag` |
| parent 3（`-u` 才有） | `untracked files on master: 805a403 add flag` |

### Q18. `reset: moving to HEAD` 是 stash 专属吗？

**不是。它是 `git reset` 的通用文案，普通 reset 也写一模一样的。**

**实测：`git stash` 会在 `logs/HEAD` 里追加一行：**

```
aeb81b0... aeb81b0... reset: moving to HEAD
└───┬───┘ └───┬───┘
   旧        新   ← 相同（HEAD 没移动，但工作区被改了）
```

**为什么 stash 会写它：`git stash` 内部第 2 步就是"把工作区 reset 回 HEAD"。**

**但普通 `git reset --hard HEAD` 写的字符串完全相同**（实测）→ **它只能当"气味"，不能当判据**。

### Q19. `git stash show -p` 的 `-p` 是什么？

**`-p` = `--patch`（补丁格式 = diff）。**

**关键：`show` 默认不是 diff：**

```
git stash show        →  2 行（--stat 统计）
git stash show -p     →  7 行（完整 diff）
```

| 等价关系（md5 实测） | |
|---|---|
| `git stash show -p` == `git stash show --patch` | ✅ |
| `git stash show` == `git stash show --stat` | ✅ |

**内部等价于：**

```
git stash show -p  =  git diff 'stash@{0}^1' 'stash@{0}'
                      （拿 stash 的 tree 和 parent 1 的 tree 比）
```

**`-p` 是 git 通用旗标：** `log -p` / `show -p` / `diff -p` / `stash show -p` 都是 patch。
**例外：`git add -p` 的 `-p` 是 interactive（分块暂存）。**

### Q20. `git stash show -p` 和 `git show 'stash@{0}:<文件>'` 有什么区别？

| | `git stash show -p` | `git show 'stash@{0}:<文件>'` |
|---|---|---|
| 输出 | **diff（改了什么）** | **文件原文（内容是什么）** |
| 要不要知道文件名 | ❌ | ✅ |
| 一次看几个 | 全部改动的文件 | 一个 |
| 实测行数 | 7 行 | 1 行 |
| 等价于 | `git diff stash^1 stash` | `git cat-file -p <blob>` |

**只要内容就选后者 —— 干净、无噪音、不用管 diff 格式。**

### Q21. 怎么知道文件名？

**文件名是随机生成的**（本例 `30172337317370.txt`），猜不到，必须查。

```bash
# ① 最常用：--stat
git stash show
#  30172337317370.txt | 2 +-

# ② 只要名字
git stash show --name-only

# ③ stash 里的全部文件 + blob 哈希
git ls-tree -r 'stash@{0}'

# ④ 全部文件名
git ls-tree -r --name-only 'stash@{0}'

# ⑤ 显式指定和哪个父比
git diff --name-only 'stash@{0}^1' 'stash@{0}'
```

**② 和 ③ 的区别：**

| 命令 | 本例数量 | 含义 |
|---|---|---|
| `git stash show --name-only` | **1 个** | 只有**改动**的文件 |
| `git ls-tree -r --name-only` | **3 个** | **全部**文件（含没改的） |

**一行搞定：**

```bash
git show "stash@{0}:$(git stash show --name-only | head -1)"
```

### Q22. `git stash pop` 为什么冲突？冲突了怎么办？

**因为 stash 的 base 和当前 HEAD 状态相反：**

```
        base            ours            theirs
      71a0ca8         1bccfa1         175c8be
    文件存在          文件被删         文件被改
        ↓
    删 vs 改 → modify/delete 冲突
```

**git 的处理：保留 stash 那一版在工作区（删数据比留数据危险）。**

```
Version Stashed changes of xxx.txt left in tree.
                      └──────┬──────┘
                    文件已经在工作区了
```

**所以冲突之后直接 `cat` 就有内容。**

**`The stash entry is kept`** = pop 在冲突时**不执行 drop**（降级成 apply），防你搞丢。

**收拾的三种方式：**

```bash
# A. 接受 stash 版本
git add <文件> && git stash drop

# B. 接受 HEAD 版本（文件仍没有）
git rm <文件> && git stash drop

# C. 只想看内容，清场
cat <文件>            # 先读！
git stash drop && git reset --hard HEAD
```

**但 CTF 里根本不需要 pop** —— 用 `git stash show -p` 或 `git show 'stash@{0}:<文件>'`，零冲突。

## 七、为什么"搬了却看不到"

### Q23. GitHack 不是把对象都搬过来了吗？为什么 `ls` 还是空的？

**搬了 ≠ 摆出来了。**

**git 里"能看到"有三层：**

```
① 工作区       ls                               ← 只有 HEAD 那个版本
② index        git ls-files --stage             ← 暂存区登记的
③ 对象库       git cat-file --batch-all-objects  ← 所有对象（最全）
```

**GitHack 只做两件事：**

| 做了 | 没做 |
|---|---|
| ✅ 下载对象到 `.git/objects/` | ❌ 不会 checkout stash / 旧提交 |
| ✅ `git reset --hard HEAD` 摆出工作区 | ❌ 不会告诉你 flag 在哪 |

**所以 `ls` 只看得到 ① 层。flag 常在第 ③ 层。**

**类比：**

| | |
|---|---|
| GitHack 搬运 | 把图书馆的书搬回家 |
| `git reset --hard HEAD` | 只把**一本书**摊在桌上 |
| `ls` | 看桌面 —— 只有那一本 |
| `git stash show -p` | 去书架把 stash 那本抽出来翻开 |

**万能兜底（不管 flag 藏在哪）：**

```bash
git cat-file --batch-all-objects --batch-check='%(objecttype) %(objectname)' \
  | awk '$1=="blob"{print $2}' \
  | while read -r h; do
      out=$(git cat-file -p "$h" 2>/dev/null | grep -oE '(ctfhub|flag)\{[^}]*\}' | head -1)
      [ -n "$out" ] && echo "★ blob $h → $out"
    done
```

**⚠️ `git fsck --unreachable` 找不到 index 里的 blob** —— 因为 index 也算"引用"，被它指向的对象是"可达"的。

### Q25. 同名 cookie 重复（新建一个同名的）会怎样？

**分两种情况：**

**① 浏览器里"新建"同名 cookie（同 domain + path）→ 覆盖，不会有两个。**

Cookie 的唯一标识是 **(name, domain, path)** 三元组：

```
name=admin, domain=xxx, path=/
    ↓ 再新建一个一样的
name=admin, domain=xxx, path=/
    ↓
浏览器: "已存在" → 【替换值】，不会变成两个
```

**② 请求头里手动塞两个（Burp / curl）→ 两个都发出去，解析器决定谁赢。**

**PHP 8.4 实测：**

| 发送的 Cookie | `$_COOKIE['admin']` | 谁赢 |
|---|---|---|
| `admin=0; admin=1` | `'0'` | **第一个** |
| `admin=1; admin=0` | `'1'` | **第一个** |
| `admin[]=1` | `[数组]["1"]` | 变数组，比较失败 |

**⚠️ 版本差异**：我测的是 PHP 8.4（first-wins）。老版本（如 PHP 5.6）可能不同，**做题要实测**：

```bash
curl -s -H "Cookie: admin=0; admin=1" "http://target/"   # 谁赢？
curl -s -H "Cookie: admin=1; admin=0" "http://target/"
```

**③ 真正的攻击技巧：Cookie Tossing**

**同名的 cookie 可以有不同的 path，浏览器把 path 更长的排在前面发。**

```
服务器设的:   name=admin, path=/         值=0
你伪造的:     name=admin, path=/admin    值=1
        ↓
请求 /admin/index.php 时发送顺序：
    Cookie: admin=1; admin=0
            ↑ 你的先发（path 更长）
        ↓
服务端取第一个 → 伪造成立
```

**这就是为什么浏览器允许"同名不同 path"的 cookie 共存 —— 它本身就是攻击面。**

## 九、一句话索引

| 问题 | 一句话答案 |
|---|---|
| `$` 和 `-s` | shell 的文本替换 vs curl 的静默开关 |
| `&&` vs `;` | 前者"成功才继续"，后者"永远继续" |
| `python` vs `python2` | Kali 上 `python` 就是 python3；GitHack 是 Py2 代码 |
| `cd` 必需吗 | 不是，GitHack 用 `__file__` 定位；`cd` 是给后面的相对路径铺路 |
| HEAD | 仓库级指针，指向分支名，不是哈希；文件没有 HEAD |
| 短哈希 | 4 位以上、唯一就行；Tab 不补全哈希 |
| `rev:path` vs `rev -- path` | 冒号取内容，`--` 过滤 diff |
| `@{0}` vs `stash@{0}` | 前者 HEAD 的 reflog，后者 refs/stash 的 |
| `log -p` 抓不到 | 目标是合并提交，`-p` 默认跳过 |
| `++` 前缀 | combined diff 按父分列，2 个父就是 `++` |
| `git rm` | 只删引用不删对象；要 `reflog expire` + `gc --prune` |
| objects/ 200 vs 403 | 200 用 `wget -r`（2 条命令），403 用 GitHack |
| `.git/index` 200 | **每个仓库都有，不能作判据** |
| Log vs Stash | `refs/stash` 存在 = Stash 题 |
| `WIP on master: xxx` | stash 本体的 message，`xxx` = parent 1 的短哈希 |
| `reset: moving to HEAD` | `git reset` 的通用文案，**不是 stash 专属** |
| `-p` | `--patch`；不加 `-p` 默认是 `--stat` |
| `show -p` vs `show :文件` | diff vs 原文 |
| 怎么拿文件名 | `git stash show --name-only` / `git ls-tree -r` |
| `pop` 冲突 | 删/改冲突，文件已 `left in tree`，直接 `cat` |
| 搬了却看不到 | 三层：工作区 / index / 对象库；GitHack 只搬不摆 |
| `50x.html` | nginx 自带的错误页模板 |
| 同名 cookie | 浏览器覆盖；请求头重复则解析器定（PHP 取第一个） |
