# 搭建全过程

> 从「我想弄一个虚拟机」到一台可用的 Windows 11 专业版虚拟机，历时约 3.5 小时
> 记录时间：2026-10-09 18:00 → 21:30

---

## 一、需求

最初的需求只有一句话：**「我想要弄一个 windows 正常用，也希望之后能用于学习 ctf」**。

拆开来是两件事：

| 需求 | 含义 |
|---|---|
| Windows 正常用 | 一台能日常使用的完整 Windows，不是阉割版、不是子系统 |
| 学习 CTF | 以后要在上面挂攻击机和靶机做渗透练习 |

第二条决定了一个硬性约束：**靶机是故意带漏洞的，网络必须隔离**。这个约束贯穿了整个方案设计（见 [CTF靶场规划.md](./CTF靶场规划.md)）。

---

## 二、环境体检

动手前先把宿主机的底摸清楚，这一步直接决定了后面所有选型。

| 项目 | 探测结果 | 影响 |
|---|---|---|
| 系统版本 | Windows 11 **家庭版** 中文版 Build 26200（25H2） | ⚠️ **家庭版没有完整 Hyper-V**，排除系统自带虚拟化 |
| CPU | AMD Ryzen 9 8945HX，16 核 32 线程 | 资源充足，给虚拟机 6 核无压力 |
| CPU 虚拟化 | BIOS 已开启（`VirtualizationFirmwareEnabled = True`） | ✅ 具备虚拟化前提 |
| 内存 | 16 GB（可用 15.3 GB） | ⚠️ 偏紧，虚拟机内存要精打细算 |
| 磁盘 | C: 剩 87.9 GB，D: 剩 106.1 GB | 虚拟机放 D 盘 |
| 已有虚拟化组件 | **WSL2 已装**（Ubuntu + docker-desktop），`VirtualMachinePlatform` 已启用 | ⚠️ **关键**：WSL2/Docker 占用了 CPU 虚拟化 |
| Hyper-V | HvHost 服务在运行 | ⚠️ 说明 Hyper-V 层已加载 |
| 未安装 | VirtualBox / VMware / QEMU 都没有 | 要新装 |
| 当前权限 | 普通用户（没提权） | 安装需要 UAC 确认 |

> 💡 **体检里最有价值的一条是「WSL2 在跑」。**
> 它意味着 Hyper-V 层已经占用了 CPU 虚拟化，第三方虚拟机软件**不能**直接用 AMD-V，必须走 **WHPX（Windows Hypervisor Platform）** 后端。
> 如果没提前发现这点，装完 VirtualBox 启动虚拟机会直接报错，然后开始盲目排查。

## 三、技术选型：为什么是 VirtualBox

四个候选逐个排除：

| 方案 | 判断 | 原因 |
|---|---|---|
| **Hyper-V**（系统自带） | ❌ 不可用 | 家庭版**不提供**完整 Hyper-V 角色，没有管理器 |
| **WSL2**（已装好） | ❌ 不满足需求 | 本质是**子系统不是虚拟机**：装不了 Windows、没有独立完整系统、做不了靶场网络 |
| **VMware Workstation Pro** | ⚠️ 可用但麻烦 | 个人免费，但**必须注册 Broadcom 账号**才能下载安装包 |
| **VirtualBox 7.2.20** | ✅ **选它** | 开源免费、官网直接下载、**Kali 官方和 VulnHub 靶机都提供 VirtualBox 镜像**，CTF 生态最省事 |

最后一条是决定性的：CTF 靶场生态里 VirtualBox 和 VMware 是主流，而 VirtualBox 免注册即可下载，省掉一个账号环节。

### 选型带来的一个隐藏前提

宿主机上 WSL2 / Docker Desktop 在运行 → Hyper-V 层占用 CPU 虚拟化 → **VirtualBox 不能直接用 AMD-V**，必须走 WHPX 后端。

实测启动日志确认了这一点：

```
HM: HMR3Init: Attempting fall back to NEM: AMD-V is not available
NEM: WHvCapabilityCodeHypervisorPresent is TRUE, so this might work...
```

**代价**：性能略低于原生虚拟化。
**收益**：与 WSL2 / Docker 共存，**不需要重启、不需要关掉 WSL2**。

> 如果哪天不需要 WSL2/Docker 了，管理员权限执行下面两行并重启，VirtualBox 就能拿到原生 AMD-V：
> ```powershell
> bcdedit /set hypervisorlaunchtype off      # 关掉后 WSL2 和 Docker Desktop 将无法启动
> bcdedit /set hypervisorlaunchtype auto     # 改回来
> ```

## 四、八个阶段

### 阶段 1 · 安装 VirtualBox

**遇到的坑**：`winget install Oracle.VirtualBox` **卡死**——翻了 winget 日志发现卡在 Windows「传递优化（Delivery Optimization）」下载环节，15 分钟零字节进展。

**改为**：从 `download.virtualbox.org` 官网直接下载，并用官方 `SHA256SUMS` 校验：

```
本地实际 : a81777d2b36380ce042a29e9c554cf032eb46a793f62e3cc82e7411e535c2c26
官方公布 : a81777d2b36380ce042a29e9c554cf032eb46a793f62e3cc82e7411e535c2c26  ✅ 一致
```

安装包 169.94 MB，静默安装 10 秒完成。

### 阶段 2 · 创建虚拟机骨架

```powershell
$vbm = 'C:\Program Files\Oracle\VirtualBox\VBoxManage.exe'

& $vbm createvm --name 'Win11-Daily' --ostype Windows11_64 --register --basefolder 'D:\VMs'
& $vbm modifyvm 'Win11-Daily' `
    --memory 6144 --cpus 6 --vram 256 `
    --chipset ich9 --ioapic on --hpet on `
    --firmware efi --rtc-use-utc off --tpm-type 2.0 `
    --graphicscontroller vboxsvga --accelerate-3d on `
    --nic1 nat --nictype1 82540EM `
    --nic2 intnet --intnet2 CTFLab `
    --clipboard-mode bidirectional --draganddrop bidirectional `
    --boot1 dvd --boot2 disk
```

**Windows 11 的三道硬门槛**必须同时满足，缺一个都装不上：

| 要求 | 配置 | 说明 |
|---|---|---|
| UEFI 固件 | `--firmware efi` | 传统 BIOS 不行 |
| Secure Boot | `modifynvram ... secureboot --enable` | 需要先登记平台密钥 |
| TPM 2.0 | `--tpm-type 2.0` | 虚拟可信平台模块 |

**Secure Boot 的坑**：不能直接 `secureboot --enable`，会报 `platform key (PK) is not enrolled`。正确顺序是：

```powershell
& $vbm modifynvram 'Win11-Daily' inituefivarstore    # 必须在首次启动之前！
& $vbm modifynvram 'Win11-Daily' enrollmssignatures  # 登记微软签名
& $vbm modifynvram 'Win11-Daily' enrollorclpk        # 登记 Oracle 平台密钥
& $vbm modifynvram 'Win11-Daily' secureboot --enable
```

> ⚠️ `inituefivarstore` **必须在虚拟机首次启动之前**执行。我先启动了一次测试，EFI 改写了变量库格式，之后所有 `modifynvram` 命令都报 `VERR_VFS_UNSUPPORTED_FORMAT`，只能删掉 `.nvram` 文件重建。

另外注意：`showvminfo` **不显示 TPM 配置**，别被它骗了。真相在配置文件 `Win11-Daily.vbox` 里：

```xml
<TrustedPlatformModule type="v2_0" location=""/>
<Firmware type="EFI"/>
```
（UEFI Secure Boot 则可以从 Windows 内部验证：`UEFISecureBootEnabled = 1`）

### 阶段 3 · 突破微软反爬拿到官方 ISO

这一步是整个过程中**最有技术含量**的部分。

**问题**：用脚本请求微软官方的 ISO 下载接口，被反爬系统拦截：

```json
{"Errors":[{"Key":"ErrorSettings.SentinelReject",
  "Value":"Sentinel marked this request as rejected."}]}
```

依次尝试了 **5 种绕过方式全部失败**：

| 尝试 | 结果 |
|---|---|
| 直接请求 connector API | ❌ SentinelReject |
| 带 Cookie 会话 + 完整 Chrome 请求头 | ❌ SentinelReject |
| curl（不同 TLS 指纹） | ❌ SentinelReject |
| 换用中国专用版本 SKU（3815 专业中文版） | ❌ SentinelReject |
| 旧版 contentinclude 接口 | ❌ 连接被关闭 |

**关键判断**：出口 IP 是**四川移动家宽**（`111.55.150.116`，非机房 IP），所以**不是 IP 被封，是请求本身缺少浏览器特征**。

**解决方案**：既然拦的是裸 HTTP 请求，那就**用真正的浏览器去点**。

用 **Node 24 内置的 WebSocket** 写了一个**零依赖的 CDP（Chrome DevTools Protocol）驱动**，启动独立 Chrome 实例并模拟真实点击：

```
接受 Cookie
  → 选择「Windows 11（适用于 x64 设备的多版本 ISO）」   （选项值 3813）
  → 点「立即下载」按钮 #submit-product-edition
  → 语言下拉框选「简体中文」                              （SKU 27157）
  → 点「确认」按钮 #submit-sku
  → 页面出现「64 位 下载」按钮，读出它的 href
```

拿到的是微软官方 CDN 直链：

```
https://software.download.prss.microsoft.com/dbazure/Windows11_Client_x64_zh-cn_26300_9457.iso?t=...
```

**结果**：`Windows11_Client_x64_zh-cn_26300_9457.iso`，**8.49 GB**，链接 24 小时有效。

> 💡 **经验**：反爬系统区分「脚本请求」和「真实浏览器」。当 API 逆向成本过高时，**用 CDP 驱动真实浏览器**是更可靠的降维打击。

**安全处置记录**：期间试过用微软官方 MCT（媒体创建工具）的命令行参数静默生成 ISO，结果 **MCT 忽略了这些参数，直接走进了「升级这台电脑」的流程**，弹出「输入产品密钥」界面。
这是全程最危险的一步——如果点下去可能会尝试升级宿主机系统。发现后立即终止了 `MediaCreationTool.exe` 和 `SetupHost.exe`，并做了三项检查确认宿主机**未被改动**：

```powershell
# 1) 无待执行的升级
HKLM\SYSTEM\Setup → SystemSetupInProgress = 0    ✅
# 2) 暂存目录只有诊断文件（0 MB）
C:\$WINDOWS.~BT   → 0.00 MB                      ✅
# 3) 无残留安装进程
SetupHost / setup / MediaCreationTool → 0 个      ✅
```

### 阶段 4 · 下载 ISO

8.49 GB，用 `curl -C -` 断点续传。

**下载速度实测**（很有趣的一段）：

| 时间点 | 速度 | 说明 |
|---|---|---|
| 开始 | 1.8 MB/s | |
| 中途 | 1.4 ~ 3.2 MB/s 剧烈波动 | 中国的家宽到微软广东移动 CDN 节点 |
| 用户出门暂停时 | 已下 3.97 GB（46.8%） | 断点保留 |
| **续传时** | **11.81 MB/s（95 Mbps）** | 线路拥塞散了，**8 分钟下完剩余 4.5 GB** |

**为什么没做多线程下载**：实测过——3 个并发连接**聚合只有 0.8 MB/s**，比单线程还慢 70%。瓶颈是线路总带宽，开多连接只会互相抢。所以坚持单线程。

**完整性校验**：下载完成的字节数与服务器 `Content-Length` 逐字节一致：

```
9,112,440,832 字节  ✅ 完全一致
SHA256: B795B52D598BF8FDEA5975844731F4A50C5713876CEFC513884354272B023AF0
```

### 阶段 5 · 无人值守安装

VirtualBox 的 `unattended install` 支持全自动安装：自动分区、建账户、跳过 OOBE、装 Guest Additions。

```powershell
& $vbm unattended install 'Win11-Daily' `
    --iso=$iso `
    --user=dsh --user-password='<密码>' --full-user-name='DSH' `
    --locale=zh_CN --country=CN --time-zone=Asia/Shanghai `
    --image-index=4 `
    --install-additions `
    --start-vm=gui
```

**选版本这一步有个关键决策**：VBox 自动探测后**默认选 `imageIndex = 1`（家庭版）**。镜像里其实有 6 个版本：

| index | 版本 |
|---|---|
| 1 | Windows 11 家庭版 ← 默认选的 |
| 2 | 家庭单语言版 |
| 3 | 教育版 |
| **4** | **专业版** ← 改成了这个 |
| 5 | 专业教育版 |
| 6 | 专业工作站版 |

改成专业版的理由：多出**远程桌面服务端、组策略编辑器、BitLocker、域加入**，这些是 Windows 域渗透靶场的前提；而且没有密钥时两者激活状态相同（都未激活），所以专业版**严格更优，不多花一分钱**。

安装耗时约 25 分钟（含几次重启），安装过程中用 `VBoxManage controlvm screenshotpng` 截图监控进度（19% → 23% → 77% → 94% → 桌面）。

### 阶段 6 · 补装 Guest Additions

**问题**：`--install-additions` 参数虽然传了，但 **GA ISO 根本没被挂载**（`SATA-2-0=none`），VBox 自己的 `VBOXPOST.CMD` 找不到 `VBoxWindowsAdditions.exe` 就**静默失败**了。

**难点**：没有 Guest Additions 就没法用 `guestcontrol` 在客户机里执行命令 —— 鸡生蛋问题。

**解决方案：键盘注入**。VirtualBox 提供 `keyboardputstring` 和 `keyboardputscancode`，可以直接往客户机"打字"：

```powershell
# 打开 Windows 搜索
& $vbm controlvm 'Win11-Daily' keyboardputscancode e0 5b e0 db    # Win 键
& $vbm controlvm 'Win11-Daily' keyboardputstring 'cmd'
& $vbm controlvm 'Win11-Daily' keyboardputscancode 1c 9c          # 回车

# 在「运行」框里注入命令
& $vbm controlvm 'Win11-Daily' keyboardputstring 'D:\VBoxWindowsAdditions.exe /S'
& $vbm controlvm 'Win11-Daily' keyboardputscancode 1c 9c
```

**三个必须知道的细节**：

| 细节 | 说明 |
|---|---|
| **UAC 弹窗默认焦点在「否」上！** | 直接回车会**拒绝安装**。正确做法：先发 `←` 方向键 `e0 4b e0 cb` 把焦点移到「是」，**再发空格 `39 b9`**（空格只激活有焦点的按钮，不触发默认按钮） |
| `keyboardputstring` 打不出引号 `"` | 路径含空格时要用 `.reg` 文件导入或 `cd` 等办法绕过 |
| 服务已注册但未启动是正常的 | `sc query VBoxService` 显示 `STATE: STOPPED` + 退出码 `1077`（ERROR_SERVICE_NEVER_STARTED），**重启一次即自动启动** |

装完后验证：

```
DISPLAY_NAME       : VirtualBox Guest Additions Service
BINARY_PATH_NAME   : C:\WINDOWS\System32\VBoxService.exe
START_TYPE         : 2   AUTO_START
```

### 阶段 7 · 修复关机死锁 ⚠️

这是全程**最难的问题**，详见 [踩坑与修复.md](./踩坑与修复.md) 的坑 7。

**症状**：关机时 Windows 显示「正在重新启动/正在关机」后永久冻结，VirtualBox 状态卡在 `stopping`，等 10 分钟不动。CPU 还在烧，磁盘完全静止。

**根因**：虚拟机配的是 **USB 平板鼠标**，它每 10ms 产生周期性中断传输，由 `VUsbPeriodFrm` 线程处理。**断电时该线程死锁**，VirtualBox 等它 60 秒超时，然后在销毁阶段永久卡住。

```
PDMR3PowerOff: 60 008 452 631 ns run time                 ← 整整 60 秒（超时特征）
PDMR3ThreadSuspend -> VERR_TIMEOUT for 'VUsbPeriodFrm'    ← 真凶
Changing the VM state from 'OFF' to 'DESTROYING'          ← 然后死在这里
```

**修复**：

```powershell
& $vbm modifyvm 'Win11-Daily' --mouse ps2
```

**三组对照实验数据**：

| 配置 | 断电耗时 | 结果 |
|---|---|---|
| USB 平板鼠标（原始） | **60.008 秒** | ❌ 死锁 |
| PS/2 鼠标 + USB 控制器关闭 | 6.7 毫秒 | ✅ 正常 |
| PS/2 鼠标 + USB 控制器开启 | 8.0 毫秒 | ✅ 正常 |

**结论**：罪魁祸首只是 **USB 平板鼠标**，不是 USB 控制器本身，所以 USB 功能（U 盘直通）得以保留。Guest Additions 已安装，鼠标集成由 GA 驱动提供，**换 PS/2 没有功能损失**。

### 阶段 8 · 建立基线快照

关机状态下建立基线快照 `干净基线`，固化最终配置。

> ⚠️ 快照必须在**关机状态**下打。第一次我在运行状态下打快照，VirtualBox 先保存了 2 GB 内存状态（`.sav` 文件），期间又发了关机命令，两个操作撞车，VM 永久卡死只能强杀进程。
