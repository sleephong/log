# 踩坑与修复

> 本次搭建共踩了 **8 个坑**，其中 2 个会导致虚拟机永久卡死（只能强杀进程），1 个有**改动宿主机系统**的风险。
> 这里记录完整的排查过程和解决方案。

---

## 速查表

| # | 坑 | 症状 | 根因 | 解决 |
|---|---|---|---|---|
| 1 | winget 装 VirtualBox 卡死 | 15 分钟零进度 | 卡在 Windows 传递优化下载 | 官网直下 + SHA256 校验 |
| 2 | 微软 ISO 接口被反爬 | `SentinelReject` | 裸 HTTP 请求缺少浏览器特征 | CDP 驱动真实 Chrome |
| 3 | **MCT 误入「升级这台电脑」** ⚠️ | 弹出「输入产品密钥」 | MCT 忽略命令行参数 | 立即终止 + 三项安全检查 |
| 4 | Secure Boot 变量库格式不兼容 | `VERR_VFS_UNSUPPORTED_FORMAT` | 首次启动改写了 NVRAM 格式 | 删 `.nvram` 重建，`inituefivarstore` 必须在首启前 |
| 5 | 无人值守安装默认选家庭版 | — | VBox 默认 `imageIndex = 1` | 显式 `--image-index=4` |
| 6 | Guest Additions 静默安装失败 | GA 属性全空 | GA ISO 没被挂载 | 手动挂载 + 键盘注入安装 |
| 7 | **关机永久卡死** ⚠️ | 卡在 `stopping` 10 分钟 | USB 平板鼠标致 `VUsbPeriodFrm` 死锁 | 改用 PS/2 鼠标 |
| 8 | **运行中打快照致卡死** ⚠️ | 卡在 `stopping` | 内存状态保存与关机操作撞车 | 关机后再打快照 |

## 坑 1 · winget 安装 VirtualBox 卡死

### 症状

```powershell
winget install --id Oracle.VirtualBox --exact --silent
```

命令挂起，**15 分钟零输出、零进度**。进程还活着，但什么都没发生。

### 排查

翻 winget 的日志，发现卡在最后一步：

```
[CORE] Downloading to path: ...\Temp\WinGet\Oracle.VirtualBox.7.2.20\a81777d2...
[CORE] DeliveryOptimization downloading from url:
       https://download.virtualbox.org/virtualbox/7.2.20/VirtualBox-7.2.20-175154-Win.exe
```

**卡在 `DeliveryOptimization`（Windows 传递优化）下载环节**。这是 Windows 的 P2P 下载组件，在某些网络环境下会挂住。

### 解决

绕过 winget，从官网直接下载并用**官方公布的哈希校验**：

```powershell
curl.exe -L -o 'D:\VMs\ISO\VirtualBox-7.2.20-Win.exe' `
  'https://download.virtualbox.org/virtualbox/7.2.20/VirtualBox-7.2.20-175154-Win.exe'

# 和官方 SHA256SUMS 比对
curl.exe -L 'https://download.virtualbox.org/virtualbox/7.2.20/SHA256SUMS'
Get-FileHash 'D:\VMs\ISO\VirtualBox-7.2.20-Win.exe' -Algorithm SHA256
```

```
本地 : A81777D2B36380CE042A29E9C554CF032EB46A793F62E3CC82E7411E535C2C26
官方 : a81777d2b36380ce042a29e9c554cf032eb46a793f62e3cc82e7411e535c2c26  ✅
```

静默安装（需 UAC）：

```powershell
Start-Process 'VirtualBox-7.2.20-Win.exe' -ArgumentList '--silent','--ignore-reboot' -Wait
```

**耗时 10 秒**。

### 经验

包管理器不是万能的。**绕开它直连官网 + 哈希校验，比修它更快**，而且哈希校验的信任级别和包管理器是一样的。

## 坑 2 · 微软 ISO 直链接口被反爬拦截

### 症状

微软官方 ISO 下载接口返回：

```json
{"Errors":[{"Key":"ErrorSettings.SentinelReject",
  "Value":"Sentinel marked this request as rejected.","Type":8}]}
```

### 排查：试了 5 种方式全部失败

| # | 尝试 | 结果 |
|---|---|---|
| 1 | 直接请求 `GetProductDownloadLinksBySku` | ❌ SentinelReject |
| 2 | 带 Cookie 会话 + 完整 Chrome 请求头（`sec-ch-ua`、`sec-fetch-*`） | ❌ SentinelReject |
| 3 | 换用 curl（不同 TLS 指纹） | ❌ SentinelReject |
| 4 | 换用中国专用版本 SKU（3815 专业中文版） | ❌ SentinelReject |
| 5 | 旧版 `contentinclude` 接口 | ❌ 连接被意外关闭 |

**关键排除**：查了出口 IP——

```
IP = 111.55.150.116   CN / Sichuan
org = AS9808 China Mobile Communications Group   ← 家庭宽带，不是机房 IP
```

`getskuinformationbyproductedition`（查版本列表）**能正常返回数据**，只有取下载直链那一步被拦。
所以**不是 IP 被封，而是这个特定接口在检查请求的浏览器特征**。

### 解决：用真实浏览器去点

思路转换：**既然拦的是裸 HTTP 请求，那就用真正的浏览器。**

Node 24 内置了 `WebSocket`，所以**零依赖**就能写一个 CDP（Chrome DevTools Protocol）驱动：

```javascript
// cdp.mjs 核心：连上 Chrome 的调试端口，在页面里执行 JS
const targets = await (await fetch('http://127.0.0.1:9222/json/list')).json()
const page = targets.find(t => t.type === 'page')
const ws = new WebSocket(page.webSocketDebuggerUrl)
// ... 发送 Runtime.evaluate 执行任意 JS
```

启动独立 Chrome 实例（独立配置目录，不碰用户原本的浏览器数据）：

```powershell
Start-Process chrome.exe -ArgumentList @(
  '--remote-debugging-port=9222',
  '--user-data-dir=D:\VMs\chrome-profile',
  '--no-first-run',
  'https://www.microsoft.com/zh-cn/software-download/windows11'
)
```

然后模拟真实点击流程：

```
接受 Cookie
  → #product-edition 设为 3813（多版本 ISO）
  → 点 #submit-product-edition
  → #product-languages 选「简体中文」（SKU 27157）
  → 点 #submit-sku
  → 读出「64 位 下载」按钮的 href
```

**拿到了官方直链**：

```
https://software.download.prss.microsoft.com/dbazure/Windows11_Client_x64_zh-cn_26300_9457.iso?t=...
```

### 经验

> **反爬系统区分「脚本请求」和「真实浏览器」。当 API 逆向成本过高时，用 CDP 驱动真实浏览器是更可靠的降维打击。**

配套技巧：把 JS 表达式**写到文件里再传参**，不要用命令行参数直接传——PowerShell 会把多行 JS 的引号搞坏。

## 坑 3 · MCT 误入「升级这台电脑」流程 ⚠️ 最危险

### 症状

用命令行参数想让微软官方 MCT（媒体创建工具）静默生成 ISO：

```powershell
MediaCreationTool.exe /EULA accept /Retail /MediaLangCode zh-CN /MediaArch x64 /MediaEdition Professional
```

**MCT 忽略了这些参数**，直接进入了 **「升级这台电脑」** 的流程，弹出一个窗口：

```
Windows 11 安装程序
产品密钥
产品密钥应该在 DVD 的包装盒上，或者在你收到的电子邮件中。
输入产品密钥
                                [上一步(B)]  [下一步(N)]
```

**如果点下去，可能会尝试升级宿主机系统。**

### 处置

发现后**立即终止进程**，然后做三项检查确认宿主机未被改动：

```powershell
# 1) 注册表里没有待执行的升级
$s = Get-ItemProperty 'HKLM:\SYSTEM\Setup'
"SystemSetupInProgress = $($s.SystemSetupInProgress)"   # 0 ✅
"SetupType = $($s.SetupType)  CmdLine = '$($s.CmdLine)'" # 0 / 空 ✅

# 2) 暂存目录只有诊断文件
(Get-ChildItem 'C:\$WINDOWS.~BT' -Recurse -File | Measure-Object Length -Sum).Sum
# 0.00 MB ✅（只够放一个 diagnostics.dat）

# 3) 无残留安装进程
@(Get-Process SetupHost,setup,MediaCreationTool -ErrorAction SilentlyContinue).Count
# 0 ✅
```

**结论：宿主机完全没有被改动**，那个窗口只是在等输入，什么都没做。

### 怎么发现「误入升级流程」的

不是靠猜，是靠**读窗口内容**。用 UI Automation 把窗口里的控件文字 dump 出来（不截屏，避免录到无关内容）：

```powershell
Add-Type -AssemblyName UIAutomationClient, UIAutomationTypes
$root = [System.Windows.Automation.AutomationElement]::RootElement
$cond = New-Object System.Windows.Automation.PropertyCondition(
    [System.Windows.Automation.AutomationElement]::NameProperty, 'Windows 11 安装程序')
$win = $root.FindFirst([System.Windows.Automation.TreeScope]::Children, $cond)
$win.FindAll([System.Windows.Automation.TreeScope]::Descendants,
    [System.Windows.Automation.Condition]::TrueCondition) |
  ForEach-Object { $_.Current.Name }
```

输出直接暴露了问题——全是「产品密钥」「输入产品密钥」「下一步」，**完全不是生成 ISO 该有的界面**。

### 经验

> **让自动化工具在宿主机上执行「安装/升级」类命令时，必须验证它真的在做你以为的事。**
> 判据不是「进程起来了」，而是「界面/日志显示的是正确的流程」。
> 这次靠 UI Automation 读窗口文字提前发现，否则后果可能是宿主机被升级。

**最终方案**：改用 CDP 驱动浏览器取官方直链（坑 2），完全不碰 MCT。

## 坑 4 · Secure Boot 的 NVRAM 变量库格式不兼容

### 症状

启用 Secure Boot 时报错：

```
VBoxManage.exe: error: Secure boot is not available because the platform key (PK) is not enrolled
VBoxManage.exe: error: Opening the UEFI variable store failed (VERR_VFS_UNSUPPORTED_FORMAT)
```

### 根因

两个问题叠在一起：

1. **没有平台密钥**：Secure Boot 必须先把 PK 登记进 UEFI 变量库才能启用
2. **变量库格式不对**：我先启动了虚拟机做测试，**EFI 改写了变量库的格式**，之后 `modifynvram` 就读不懂了

### 解决

删掉 `.nvram` 文件重建，**严格按顺序**执行：

```powershell
Remove-Item 'D:\VMs\Win11-Daily\Win11-Daily.nvram' -Force

& $vbm modifynvram 'Win11-Daily' inituefivarstore    # 初始化变量库
& $vbm modifynvram 'Win11-Daily' enrollmssignatures  # 登记微软签名（让 Windows 能启动）
& $vbm modifynvram 'Win11-Daily' enrollorclpk        # 登记 Oracle 平台密钥（解决 PK not enrolled）
& $vbm modifynvram 'Win11-Daily' secureboot --enable
```

验证：

```
PK                               {8be4df61-93ca-11d2-aa0d-00e098032b8c}
KEK                              {8be4df61-93ca-11d2-aa0d-00e098032b8c}
SecureBootEnable                 {f0a30bc7-af08-4556-99c4-001009c93a44}
```

### 两个容易误判的地方

| 误判 | 真相 |
|---|---|
| `showvminfo` 里看不到 TPM 配置 | **这是 VirtualBox 的显示缺陷**。真相在 `Win11-Daily.vbox` 里的 `<TrustedPlatformModule type="v2_0" location=""/>` |
| 以为 Secure Boot 没生效 | 从 Windows 内部查才准：`HKLM\SYSTEM\CurrentControlSet\Control\SecureBoot\State` → `UEFISecureBootEnabled = 1` |

### 经验

> `inituefivarstore` **必须在虚拟机首次启动之前**执行。顺序错了就得删文件重来。
> 配置类问题不要只看 `showvminfo` 的输出，**直接读配置文件 `.vbox`**（XML）才是真相。

## 坑 5 · 无人值守安装默认选了家庭版

### 症状

`VBoxManage unattended install` 输出：

```
detectedOSFlavor = Core
imageIndex       = 1
detectedImage[0]* = #1: Windows 11 家庭版 (10.0.26300.9457 / x64 / zh-CN)
detectedImage[1]  = #2: Windows 11 家庭单语言版
detectedImage[2]  = #3: Windows 11 教育版
detectedImage[3]  = #4: Windows 11 专业版
detectedImage[4]  = #5: Windows 11 专业教育版
detectedImage[5]  = #6: Windows 11 专业工作站版
```

**默认选了 `imageIndex = 1`（家庭版）**。

### 为什么要改

| 能力 | 家庭版 | 专业版 |
|---|---|---|
| 远程桌面**服务端**（RDP） | ❌ | ✅ |
| 组策略编辑器 `gpedit.msc` | ❌ | ✅ |
| BitLocker | ❌ | ✅ |
| 域加入（Windows 域渗透靶场前提） | ❌ | ✅ |
| 激活状态（无密钥时） | 未激活 | 未激活 |

**专业版严格更优，不多花一分钱。**

### 解决

发现时安装才启动 11 秒，成本极低，直接重做：

```powershell
& $vbm controlvm 'Win11-Daily' poweroff        # 关掉刚启动的
& $vbm unattended install 'Win11-Daily' ... --image-index=4 --start-vm=gui
```

验证：

```
detectedOSFlavor  = Professional
imageIndex        = 4
```

从 Windows 内部二次确认：

```
EditionID   : Professional
DisplayVersion : 26H2
```

### 经验

> **无人值守 ≠ 无需检查。** 自动化的默认值往往是「最小公分母」，必须核对它到底选了什么。
> 关键指标：`detectedOSFlavor` 和 `imageIndex`。

## 坑 6 · Guest Additions 静默安装失败

### 症状

`unattended install` 带了 `--install-additions` 参数，但装完后：

```powershell
& $vbm guestproperty enumerate 'Win11-Daily'
# 完全没有 GuestAdd/Version 之类的属性 → GA 没装
```

检查光驱：

```
"SATA-1-0" = "D:\VMs\Win11-Daily\Unattended-...-aux-iso.viso"
"SATA-2-0" = "none"     ← Guest Additions ISO 根本没被挂载！
```

### 根因

VBox 的无人值守流程会生成一个 `VBOXPOST.CMD`，由 `autounattend.xml` 的 `FirstLogonCommands` 在首次登录时执行。这个脚本里写的是：

```batch
set MY_VBOX_ADDITIONS=E:\vboxadditions
if exist %MY_VBOX_ADDITIONS%\VBoxWindowsAdditions.exe goto found_vbox_additions
set MY_VBOX_ADDITIONS=D:\vboxadditions
...
```

**它按 D:/E:/F:/G: 逐个找 GA 光盘，但那张光盘压根没被挂上**，于是全部命中失败，**静默退出**（没有任何报错）。

### 难点：鸡生蛋问题

没有 Guest Additions 就没法用 `guestcontrol` 在客户机里跑命令 —— 但装 Guest Additions 又需要在客户机里跑命令。

### 解决：键盘注入

VirtualBox 提供了直接往客户机"打字"的能力：

```powershell
# 1) 把 GA ISO 挂到光驱（autounattend.xml 证实客户机光驱盘符是 D:）
& $vbm storageattach 'Win11-Daily' --storagectl 'SATA' --port 1 --device 0 `
    --type dvddrive --medium 'C:\Program Files\Oracle\VirtualBox\VBoxGuestAdditions.iso'

# 2) 打开 Windows 搜索并输入 cmd
& $vbm controlvm 'Win11-Daily' keyboardputscancode e0 5b e0 db   # Win 键
& $vbm controlvm 'Win11-Daily' keyboardputstring 'cmd'
& $vbm controlvm 'Win11-Daily' keyboardputscancode 1c 9c         # 回车

# 3) 在「运行」框里注入安装命令
& $vbm controlvm 'Win11-Daily' keyboardputstring 'D:\VBoxWindowsAdditions.exe /S'
& $vbm controlvm 'Win11-Daily' keyboardputscancode 1c 9c
```

### ⚠️ 最关键的细节：UAC 的默认焦点在「否」上

弹出来的 UAC 是这样的（**「否」带蓝色高亮**）：

```
用户账户控制(UAC)
你要允许此应用对你的设备进行更改吗?
Oracle VirtualBox Guest Additions
已验证的发布者: Oracle Corporation
                          [ 是 ]  [ 否 ]     ← 「否」是默认按钮
```

**直接按回车会点到「否」，安装被拒绝。**

正确做法：

```powershell
# 先按 ← 方向键把焦点移到「是」
& $vbm controlvm 'Win11-Daily' keyboardputscancode e0 4b e0 cb
# 再按空格 —— 空格只激活【有焦点】的按钮，不会触发默认按钮
& $vbm controlvm 'Win11-Daily' keyboardputscancode 39 b9
```

> **为什么用空格不用回车**：回车触发的是**默认按钮**（还是「否」），空格触发的是**有焦点的按钮**。这是本次学到的关键操作技巧。

### 其它两个细节

| 细节 | 说明 |
|---|---|
| `keyboardputstring` **打不出引号 `"`** | 实测 `dir "C:\Program Files\Oracle"` 注入进去变成了 `dir C:\Program Files\Oracle`（引号丢失）。路径含空格时改用 `.reg` 文件导入等办法绕过 |
| 服务注册了但显示 STOPPED 是正常的 | `sc query VBoxService` → `STATE: 1 STOPPED`、`WIN32_EXIT_CODE: 1077`（ERROR_SERVICE_NEVER_STARTED），**重启一次就自动启动** |

### 验证方法（无 GA 时如何看到客户机内部信息）

用键盘注入开一个命令行，让命令**把结果打在屏幕上**，然后 `screenshotpng` 截图 + 读图：

```powershell
& $vbm controlvm 'Win11-Daily' keyboardputstring 'sc qc VBoxService'
& $vbm controlvm 'Win11-Daily' keyboardputscancode 1c 9c
& $vbm controlvm 'Win11-Daily' screenshotpng 'D:\VMs\logs\check.png'
```

截图上直接读到：

```
BINARY_PATH_NAME   : C:\WINDOWS\System32\VBoxService.exe
START_TYPE         : 2   AUTO_START
DISPLAY_NAME       : VirtualBox Guest Additions Service
```

**这是没有 Guest Additions 时验证客户机状态的可靠手段。**

## 坑 7 · 关机永久卡死 ⚠️ 最难的问题

### 症状

关机时 Windows 界面显示「正在重新启动」或「正在关机」后**永久冻结**：

- VirtualBox 状态卡在 `stopping`，等 10 分钟也不动
- **CPU 还在烧**（约 1.5 核），**磁盘却完全静止**
- 强制按 ACPI 电源键无反应
- 只能强杀 `VirtualBoxVM` 进程

### 排查过程（三步走）

#### 第一步：排除快速启动（失败）

第一反应是 Windows 快速启动（混合关机）在虚拟机里容易出问题：

```powershell
powercfg /h off        # 关闭休眠
```

注册表 `HiberbootEnabled` 也改成 0，`hiberfil.sys` 已删除。

**结果：关机依然卡死。** 排除这个方向。

#### 第二步：分析卡住的进程（找到方向）

```powershell
$proc = Get-Process VirtualBoxVM | Sort-Object CPU -Descending | Select-Object -First 1
$proc.Threads | Group-Object ThreadState
$proc.Threads | Group-Object WaitReason | Sort-Object Count -Descending
```

输出：

```
15 秒 CPU 增量: 0.0 秒          ← 完全静止
线程数: 132
Wait 状态: 132 个（全部）

等待原因分布:
  UserRequest     123
  EventPairLow      5
  Executive         2
  LpcReply          2      ← 卡在等进程间调用的回复
```

**判断**：CPU 增量为 0 → 不是死循环，是**死等（deadlock）**。

同时看客户机自己的日志，发现**客户机操作系统其实每次都正常关机完了**：

```
VMMDev: Guest requests the VM to be turned off
Changing the VM state from 'RUNNING' to 'POWERING_OFF'
...
End of statistics
VUSB: Detached 'HidMouse' from port 1 on RootHub#0
```

**所以卡的是 VirtualBox 自己，不是 Windows。**

#### 第三步：挖 VBox.log（找到根因）

在日志里定位到决定性的三行：

```
00:02:37.755158  PDMR3ThreadSuspend -> VERR_TIMEOUT for 'VUsbPeriodFrm'
00:02:37.755184  Changing the VM state from 'POWERING_OFF' to 'OFF'
00:02:37.760158  Changing the VM state from 'OFF' to 'DESTROYING'
```

往前看断电耗时：

```
00:01:37.745873  Changing the VM state from 'RUNNING' to 'POWERING_OFF'
00:02:37.755172  PDMR3PowerOff: 60 008 452 631 ns run time
                 ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 整整 60 秒
```

**60.008 秒 = 超时的典型特征**（不是真在干活，是在等超时）。

### 根因

**`VUsbPeriodFrm`（USB 周期帧线程）死锁。**

虚拟机配的是 **USB 平板鼠标**（绝对定位设备）：

```xml
<HID Pointing="USBTablet"/>
<USB><Controllers><Controller name="OHCI" type="OHCI"/></Controllers></USB>
```

USB 平板作为 HID 设备，**每 10ms 产生一次周期性中断传输**，正是由 `VUsbPeriodFrm` 线程负责处理的。
**断电时这个线程死锁 → VirtualBox 等它 60 秒超时 → 然后在销毁（DESTROYING）阶段永久卡住。**

### 解决

```powershell
& $vbm modifyvm 'Win11-Daily' --mouse ps2
```

### 三组对照实验（确定修复边界）

为了搞清楚是「USB 平板」的问题还是「USB 整体」的问题，做了对照实验：

| 配置 | `PDMR3PowerOff` 耗时 | 结果 |
|---|---|---|
| **USB 平板鼠标**（原始配置） | **60.008 秒** | ❌ 死锁，状态永远停在 `stopping` |
| PS/2 鼠标 + USB 控制器关闭 | 6.7 毫秒 | ✅ 正常 |
| **PS/2 鼠标 + USB 控制器开启** | **8.0 毫秒** | ✅ **正常** |

**结论：罪魁祸首只是 USB 平板鼠标，USB 控制器本身没问题。**
所以 **USB 功能（U 盘直通）得以保留**，只需要把鼠标换成 PS/2。

**功能损失为零**：Guest Additions 已安装，鼠标集成由 GA 驱动（`VBoxMouse.sys`）提供，不依赖 USB 平板。

### 经验

> 1. **看 CPU 曲线区分死锁和死循环**：CPU 为 0 = 死等，CPU 满 = 死循环。两者排查方向完全不同。
> 2. **精确到毫秒的整数时间 = 超时**：60.008 秒、120.000 秒这种数字，说明是在等某个超时，不是在干活。
> 3. **客户机日志和宿主机日志要分开看**：这次客户机（Windows）一点问题都没有，问题全在 VirtualBox 自己的设备模拟层。
> 4. **对照实验是确定修复边界的最快方式**：一次改一个变量，三组数据就能锁定「到底是哪个组件」。

## 坑 8 · 在运行中打快照导致永久卡死 ⚠️

### 症状

给运行中的虚拟机打快照：

```powershell
& $vbm snapshot 'Win11-Daily' take '干净基线'
```

`Snapshot taken.` 看起来成功了。但之后的关机操作让 VM **永久卡在 `stopping`**，只能强杀进程。

### 根因

看 `Snapshots` 目录发现了证据：

```
2086.99 MB  2026-10-09T12-56-01Z.sav      ← 2 GB 的【内存状态保存】文件
  809.00 MB  {b7aab978-...}.vdi          ← 差分磁盘
```

**VirtualBox 给运行中的虚拟机打快照时，会先把整个内存状态（6 GB 内存 → 2 GB 压缩）保存成 `.sav` 文件**，这个过程需要一段时间。

时间线暴露了撞车：

```
20:55     发起快照
20:56:01  .sav 内存状态开始写入
20:56:20  ← 我在这个时间点发了关机命令（快照还没写完！）
20:56:41  差分磁盘创建完成
20:57:49  VM 进入 stopping，然后永久卡住
```

**两个操作撞车了**：内存状态保存 + 关机流程互相等待，形成死锁。

### 解决

**正确流程：先关机，再打快照。**

```powershell
# 1) 先正常关机
& $vbm guestcontrol 'Win11-Daily' run --exe 'C:\Windows\System32\shutdown.exe' `
    --username 'dsh' --password '<密码>' -- /s /t 5
# 等状态变成 poweroff

# 2) 确认已关机
& $vbm showvminfo 'Win11-Daily' --machinereadable | Select-String '^VMState='

# 3) 再打快照
& $vbm snapshot 'Win11-Daily' take '干净基线'
```

### 卡死后的抢救方法

```powershell
# 正常断电会被拒绝（"The virtual machine is being powered down"）
& $vbm controlvm 'Win11-Daily' poweroff        # ❌ VBOX_E_INVALID_VM_STATE

# 只能强杀进程
Get-Process VirtualBoxVM | Sort-Object CPU -Descending |
    Select-Object -First 1 | Stop-Process -Force
# 之后 VM 状态变成 aborted，磁盘数据完好（Windows 能正常启动）

# 删掉带内存状态的快照（会合并差分磁盘）
& $vbm snapshot 'Win11-Daily' delete '快照名'
```

### 经验

> **虚拟机快照不是「拍照」，运行状态下打快照 = 保存 6 GB 内存。**
> 期间任何其它 VM 操作（关机、改配置、再打快照）都可能撞车。
> **养成习惯：关机 → 打快照 → 开机。**

## 总结：这次的通用教训

| 教训 | 具体体现 |
|---|---|
| **自动化 ≠ 免检** | MCT 忽略了参数跑进了升级流程、unattended install 默认选了家庭版——都必须**核对它实际做了什么**，而不是假设 |
| **看数据，不看现象** | 「关机卡住」这个现象背后，是 60.008 秒的超时、132 个 Wait 线程、`VERR_TIMEOUT for 'VUsbPeriodFrm'` 这三组数据定位的 |
| **客户机和宿主机日志分家** | 客户机每次都正常关机完了，问题全在 VirtualBox 设备模拟层 |
| **对照实验锁定边界** | 三组配置（USB平板 / PS2+USB关 / PS2+USB开）一次就把根因范围缩到单个组件 |
| **绕过比硬刚更快** | winget 卡死→官网直下；反爬拦截→CDP 驱动浏览器。**都不去修那个坏掉的东西** |
| **官方哈希必须校验** | VirtualBox 安装包和 Windows ISO 都做了字节级校验，避免被篡改的安装介质 |
| **危险操作前先想好怎么撤** | 修 Secure Boot 前先看清楚顺序；改配置前有基线快照兜底 |
